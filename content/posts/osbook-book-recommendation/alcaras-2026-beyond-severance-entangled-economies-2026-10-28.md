## 一点推荐

先把这篇的动机说清楚，因为它不是在争论一个结论，而是在争论一把尺子。

过去二十年，研究开源的主流方式是：把「社区」和「公司」预设为两个世界，然后去观测它们如何相遇。相遇得好，叫「良性互动」；相遇得坏，叫「资本捕获」「圈地」「搭便车」。Alcaras 把这种预设命名为 **severance（分离）**——注意，他说的不是某篇论文算错了，而是整个领域默认的**观测框架**错了。

他的检验对象是 Git。不是随便挑的：Git 是那个「无人拥有、却承载几乎每一行代码」的东西，它天生就卡在教科书的两个世界之间。

数据是三层叠起来的：

- **田野**：2016-09 至 2020-01，约三年，11 场产业活动（巴黎、巴塞罗那、伦敦、布鲁塞尔、旧金山，多数有企业赞助），约 50 次非正式交流，25 场半结构化访谈，还亲自参与编码活动（含一次 hackathon 与协助 Git Rev News 通讯）。
- **数字痕迹**：邮件列表 393,811 封（9,530 名发件人，可标注量占 63.2%）、代码仓库 58,450 个 commit（1,750 名贡献者，可标注量占 82.3%），覆盖 2005 年立项至 2020 年田野结束。
- **手工标注**：对 205 名「每个季度贡献 80% 以上 commit」的开发者逐个编码劳动状态与雇主轨迹，最终识别出 146 人（71%）的职业位置，其余 59 人记为 unknown（作者判断「大概多为志愿者」）。

三个结论，一个比一个不稳：

**一、Git 的顶级贡献者几乎全是有工作的专业人士。** 76.7% 在软件业（工程师 45.7%、开发者 16.3%、其他编程岗 9.8%、高管 2.7%、系统管理员 2.1%），16.8% 在学界（学生 9.2%、教职 7.6%），6.5% 靠 GSoC / Outreachy 的资助。雇主名单里 Google 18 人、GitHub 9 人、Facebook 6 人、GitLab 与 Microsoft 各 3 人。学历也离谱：在 125 名已知学历者中，43% 本科、37% 硕士、**20% 博士**（对照 Stack Overflow 2021 调查的 50% / 25% / 3%）。女性只有 3 人，占 1.5%。

**二、但被公司付钱写 Git 的，长期只有一成。** 2005 年二季度 paid 贡献者占 51%（Torvalds 等核心内核黑客本就受薪），到三季度就跌到 20%，此后多年在 5% 上下，「2015 年以后」大致维持在 10% 上下（Figure 1 与正文表述）；2010 年起有约十位贡献者陆续获得资助，多为大公司雇员——维护者在 2010 年公开写道「我最近入职了 Google」。到 2020 年一季度：活跃贡献者 80 人，其中受薪者占 10%，**却写了 956 个 commit 中的 60%**。

第一条和第二条并排放在一起，才是这篇论文真正的位置：**绝大多数人不是被雇来写 Git 的，但他们几乎全都被别处雇着写软件。** 「志愿」并不等于「业余」，更不等于「在产业之外」。

**三、时间戳把「分离」的最后一个证据也拆了。** 常规假设是：志愿贡献发生在夜晚和周末，受薪贡献发生在办公时间。k-means 把 254 条「贡献者-年」时间序列（55 人，每条年均邮件数 > 200）聚成三类，对照劳动状态（Table 4，χ² 检验 p < .05）：

- 第一类，每晚都有活动：paid 28.7% / partially paid 9.3% / **volunteer 62.0%**；
- 第二类，办公时间一个峰、深夜一个峰的双相节奏：paid 30.0% / partially paid 20.0% / **volunteer 50.0%**；
- 第三类，几乎完美贴合工作日办公时间：**paid 59.1%** / partially paid 13.6% / volunteer 27.3%。

注意三件事。第一，**每一类里都有大量「错位」的人**：最像志愿者的那一类里有 28.7% 是受薪的；最像上班族的那一类里有 27.3% 分文不取。第二，**周末根本不是志愿者的主场**——作者的原话是，真正可靠的区分不是「工作日 vs 周末」，而是「白天 vs 夜晚」。第三，一部分志愿者的活动**恰好发生在办公时间**：他们是在公司的服务器、网络、场景（高频交易、动画工作室）里撞到 Git 的 bug，修完再上游回去。有位替 Google 维护内部 Git 基础设施的工程师在邮件列表里写：「我改 Git 是因为好玩（这跟我为糊口做的乏味编码不一样），也因为我想用它帮我做那份乏味的工作。但我改 Git 的时候，可没人给我一分钱。」——作者把这句话定性为 **boundary work**：一种不敌对、却持续生产「分离」效应的边界工作。

于是全文的枢轴就出来了：**severance 不是事实错误，是观测装置的误差。** 因为它错，一批本该被看见的东西系统性不可见——「同一个人在同一个工作日的同一小时里，既是雇员又是志愿者」这件事，在两分法里根本没有格子可放。

## 内容概要

**概念解剖（第二节）。** 作者把批判目标定得很准：不是某篇论文的结论，而是整个领域的默认框架。他引 Zelizer 2005 对货币与亲密关系的分析，指出这种关系总被读成两种语法之一——「敌对世界」（hostile worlds：程序员 vs 公司、项目 vs 企业、社区 vs 资本，一切纠缠都被说成「政治、经济、道德的暧昧」）或「不过是」（nothing but：一切纠缠都被说成「资本主义占有」、免费劳动的捕获、礼物经济的积累、物流权力的控制）。两种语法共用同一个前提：**社区与公司在此之前就已经是两个东西了**。所以当它们「相遇」，它变成了一个需要被解释的事件，而不是证据——证据本该是：它们从来就没分开过。

**「纠缠经济」（entangled economies）作为替代。** 关键词两个：**异质（heterogeneous）** 与 **编织（woven）**。作者用 Callon & Latour 的说法，把纠缠定义为「比形成它们的互动活得更久的联合」——结，会留下来。这些结里织着**至少四种逻辑**：价值捕获、企业控制、对基础设施的照护（care，引 Denis & Pontille 2025）、以及贡献者自己称为 **"real work"** 的投入（引 Bidet 2011）。因此「这段代码是公司的还是社区的」在方法上是个**范畴错误**——它假定一段劳动只能属于一种逻辑。

**「产业性公共品」（industrial public good）。** 作者明确说，之所以不用「公地」或「社区」，是因为这两个词**自带 severance 的余味**。他改用 Polanyi 1977 的实质主义经济观：把「产业」理解为支撑数字生产的**全部工作与经济制度的总和，无论市场与否**。这个概念源自经济学（Romer 1993：非竞争、非排他、企业有激励共同生产的资源），曾被用于 Linux（Jullien & Zimmerman 2013），近年被社会学家重拾（Alcaras 2020；O'Neil et al. 2024）。在 Git 这里：**使用上像公共品，维持上像产业设施。**

**方法论（第三节）。** 这一节值得单独看，因为它把「为什么过去看不见」讲成了一个可操作的技术问题。大规模研究只能靠**邮箱域名**或**活动时间**推断受薪状态（Claes et al. 2018；O'Neil et al. 2024）——这是规模上唯一可行的办法，但代理不可靠。作者因为规模小，选了更笨也更稳的路：**手工编码，且以自我陈述为准**——除非某人明确说 Git 是其带薪职责的一部分，否则记为无偿。四种状态：Paid（全职做 Git 是工作）/ Partially paid（公司时间 10–20% 给 Git）/ Volunteer（知道日常工作但未主张为 Git 受薪）/ Unknown（证据不足，多数大概是志愿者）。

有个细节非常锋利：整个 Git 仓库里**只有十几个 commit 提到带薪工作，只有三个标了 "sponsored"**，而其中一个是说微软捐了云资源，**没提作者本人在微软上班**。作者对这件事的解读是全文最重的一句：这个空白**不是** Git 与产业之间存在自然边界的证据，它是贡献者通过话语实践**主动表演出来**的「敌对世界」，是 severance 的再生产。

**田野证据（第五、六节）。** 除了上面三组数，还有几条特别值得抄：

- 「自己挠自己的痒」这条开源老话在这里有了物质版本。有个 commit 直接感谢老板催他改：*"When my boss has something to show me and I have to update... git pull refuses to work in such a case. I wrote this little script..."* —— 一个 patch 的作者署名、提交时间、代码内容全都指向同一件事：**连纯粹的志愿提交，也可能是工作场所留下的指纹。**
- 受薪者的劳动**大量不产生上游痕迹**。很多人实际在做同事的内部咨询：「前端的人常过来问『我们想做这个，该怎么做』，我就告诉他们『这个项目会希望你怎么做』。」
- 受薪者自己描述的是 **guidance 而非 task list**：「他们确实给了指导，说这些是值得修的痛点。但我一直觉得总的任务是搞清楚项目需要什么，然后去做。你要真想支持一个开源社区，就得这么做——因为你要按自己公司项目那样管它，上游会恨你。」作者由此提出一个反直觉的判断：**企业资源再多，也管不住 FOSS 项目，甚至管不住自己雇来的人。**
- 「小事的工作」（little work）vs「大事的工作」（big work）：「我一个月没写过几行代码，但我花了巨量时间在社区健康上」；另一位自估 **50% 读邮件列表、25% 回邮件、只有 25% 写代码**。这段引文值得整段抄下来：

> 「对我来说开源最可爱的地方是：我醒来，中午了，从床上滚下来，晃到电脑前，开始看邮件列表，有人说『嘿我在做这个，好像不太对，这挺怪的』。我说『哦，确实怪』……到一天结束，你说『哦，这就是我整个工作日了』，但我最后拿到了六个 patch：其中四个是急需的清理，一个是我在查另一个 bug 时发现的 bug，还有一个才是那个人真正想要的那个。我的雇主可能更希望我多做点『大事』，但我也觉得『小事』是保持社区健康的非常重要的部分。它在修 bug，在清理代码，在给邮件列表里的其他人做行为示范。」

- 雇佣改变的是**节奏**而不是**产出量**：入职后 Git 工作挪进白天、周末变成禁区、22:00–05:00 的夜间活动下降（坐班的下降最明显，远程的保留弹性）；但**贡献量没有可靠变化**。这直接反驳了「志愿贡献只是为了找工作」的动机假说。

**「理性的梦想」（第八节）。** 作者借 Weber 1986 的说法，把志愿贡献理解为一条**可延续为职业的平行路径**：多数人并不明确追求它，但很多人承认这个可能性——把 FOSS 当有回报的爱好，养着一个「理性的梦想」。而通道是晦暗的：这类岗位几乎不出现在招聘启事上，靠私人关系。作者的措辞很讲究：用「被雇佣」描述，正确地强调了企业意图，**风险却是压低贡献者的能动性**——他们往往在利用自己的位置，支持自己认为的「真正的工作」。

**异质逻辑（第九节，全文最细的部分）。** 企业的技术议程真实存在：GitHub 要面向主流开发者做 Web 平台，就推动修 Git 那个老内核黑客几乎不用的不安全 HTTP 认证（他们偏好 SSH）；能出钱的大公司想让 Git 撑住巨大代码库与团队规模。企业面对 fork 与上游的权衡：内部 fork 快、可控、但积技术债；上游合并慢（可达数年）、不确定、但把维护外部化给项目。**多数公司两样都做**。

但即便在这条最「公司化」的路径上，逻辑也不单一。有位贡献者跟经理吵过：经理说「你该为团队做点工作了，现在你自己决定做什么，那不算工作」。也就是说，**在同一个受薪身份里，企业目标与贡献者的承诺仍然能打架**。作者由此收束：产业性公共品**未必与主流开发方式兼容**；企业尽管有战略与资源，仍难以像自己希望的那样控制项目。

**书写的分寸。** 作者自己留了后门：这是**单案例**。他点名了三个对照方向——Debian 需要为它的纠缠做**修辞上的正当化**（O'Neil et al. 2021b），Chromium 这类由单一公司发起的项目更接近传统管理，而长尾小项目里的纠缠大概主要靠无偿劳动中介。对 AI，他提了一个克制的方向：要问的不是「开源 AI 是不是开源」，而是「**1980 年代让自由软件得以出现的那些条件，今天还在不在**」——以及生产链上哪些环节可以被公司内部化、哪些不能，那些不能的，才可能是产业性公共品的候选。

## 一句话推荐

**这不是一篇「企业参与开源是好是坏」的论文，而是一篇论证「我们一直用来回答这个问题的尺子本身刻错了」的论文。**

## 为什么值得读

**一、因为它把「批判」的对象从对象换成了装置。** 我们读过的很多开源经济学实证，默认变量表里就有「公司 vs 社区」这一列。这篇说：这一列不是数据里长出来的，是你带进田野的。一旦带进去，你就会看见「受薪即失去自主」这样的结论——而它可能只是**工资这个代理变量**说了太多话。作者对 O'Neil et al. 2024 的评价很有分寸：那些发现是有效的，但可能夸大工资单独能说明的东西，「也许过于机械地把它当成自主性的终点」。这句话值得所有拿邮箱域名当受薪标志的量化研究抄在墙上。

**二、因为它是把「方法论考古」做成实证的罕见样本。** 说「两分法有害」很容易，难的是**证明它会漏掉什么**。作者的做法是：先建一套能把状态标出来的数据（205 人、71% 识别率、82.3% commit 覆盖），再拿它去照那套两分法。照出来的不是「有些例外」，而是「三个聚类的每一类里都有大比例错位者」。这是可以在方法上被检验的批评，不是立场表达。

**三、因为它给了「不可见」一个可命名的机制。** 全文最有生产性的发现是那个空白：58,450 个 commit 里，只有十几个提到受薪，三个标 sponsored。这个空白**看起来**像证据（「看，Git 与产业无关」），实际上是**贡献者主动擦掉的痕迹**。这跟 Scott 的「可被记录的才被看见」是同一机制的另一面：不是记录者遗漏，而是被记录者有意识地不做记录。研究者如果拿「commit message 里没写」当作独立性证据，就把**表演**读成了**事实**。

## 为什么对开源社区如此重要

**第一，它替换了「公共品 / 俱乐部品」这组分类的落点。**

我们此前反复用「开源是俱乐部品而非公共品」来刻画开源：**准入**上有章程、有边界、有人决定谁能进来，所以不是公共品。Alcaras 这篇既不是推翻也不是绕开，而是**把另一半补上**：俱乐部品回答**准入**，产业性公共品回答**维持**——谁在照护它、按谁的时钟照护、照护的劳动从哪来。**同一件东西，准入上是俱乐部，维持上是产业设施。** 这个双层刻画比单层精确得多，因为它解释了原命题解释不了的事：为什么一个「有边界的俱乐部」，其维护者的工资条却来自俱乐部之外。

他不肯用「公地」这个词的理由也值得记住：**「公地」和「社区」自带 severance 的余味**——听起来像「公司之外的那个世界」。这个措辞上的洁癖，是这篇文章最见功力的地方之一。

**第二，它给 Ostrom 第 8 条（分层治理）出了一个很难的题。**

分层治理预设存在一个**能划边界的主体**。Git 的困难恰恰是：没人拥有它，因此没人有资格划那条界。Alcaras 的表述是——治理确实在发生，但**没有治理者**。这与我们读过的几篇构成一个同构系列：「关停仓库的出处审计」里的无中心权威证据边界、「Assisted-by 从规则挪进叙述」里的谁有资格认定、以及本文的「谁有资格划界」。三处空在同一个位置。

**第三，它把 Polanyi 的嵌入论调转了个方向。**

「分离」预设其实是「市场脱嵌」幻觉的**镜像版**：把市场想象成脱嵌于社会，与把 FOSS 想象成脱嵌于市场，是同一个错误的两个方向。**你以为自己在批判市场化，其实你在重复市场化的语法。** 这个转向对「开源之道」是一记直拳：如果我们把开源描述成一个不该被市场污染的世界，我们就已经接受了「世界可以被切开」这个前提。

**第四，它为「评价体系不可通约性」补上了劳动侧的形态。**

贡献者把某一类劳动命名为 **"real work"**，这件事本身就是一个制度性命名行为——**需要自己命名，是因为没有现成的制度承认它**。这与我们此前观察到的「参与被承认、参与的定义不被承认」的断层同源，也正好接上「功绩制 vs 权力制不可通约」——同一份劳动，在两套评价体系里得到完全不同的承认。而 Alcaras 的材料给出了这个不可通约的**日常形态**：读邮件列表、回邮件、修别人的 bug、给同事做内部咨询，全是「小事的工作」，全难以进入任何一张贡献图。

**第五，也是最重要的一点：它对「大分流 2.0」提出了一处必须承认的边界。**

这里要做个区分，否则会读错。

- Alcaras 拆的是**领域内部的**方法论二分：社区 vs 公司，志愿 vs 受薪。
- 我们做的大分流 2.0 拆的是**跨制度环境的**比较：真开源的公地形态 vs 行政动员的替代形态。

两者不在同一层，**因此不冲突，也不互相覆盖**。但 Alcaras 的框架一旦挪进中国语境，会立刻换形：他的「产业性公共品」指的是**由产业共同体承担**的维持——Google 的工程师、GitHub 的雇员、Red Hat 的投入。而在本土语境里，承担「产业性」的往往**不是产业共同体，而是国家与平台**。按我们此前对托管平台自建、高校镜像、行政合规标准、封闭社群变现的多路径观察，这条链条上每一环都有提供者，但没有一环是产业自发的。

**所以大分流 2.0 在 Williamson L1 社会嵌入层最深的一处差异，可能不是「开不开源」，而是「产业性由谁承担」。** 这一句是本文的推论，不是作者的观点——作者对中国的语境完全缺席，全篇没有一个中国案例。但恰恰因为缺席，这处对照才显得必要。

## 一段自我约束：这篇论文做到了什么程度

**它做得很扎实的地方：**

1. **状态判定以自我陈述为锚，且明确交代了代价。** 作者承认这条规则会把「在办公时间改 Git 却不认为自己是带薪」的人记成 volunteer，并明说很多案例落在中间地带——工程师确实在办公时间打 patch，却仍自述为无偿。这不是数据瑕疵，这是他论证的**原材料**：那一层模糊本身就是纠缠。
2. **数据可得性是真的。** 匿名数据集 + 复算代码挂在 GitHub 上，补充材料公开。相对于十月里读到的一批只能在摘要层批评的预印本，这篇的核验入口是敞开的。
3. **对自己的工具做了检视。** 他点出「邮箱域名」这个通行代理的可靠性问题，并解释了自己为什么选了成本更高但更稳的路线。
4. **没有把结论推过头。** 全文落在「单一案例」「未来工作应做比较」上，而不是「所有开源项目都如此」。

**它的限制，以及我要补的：**

1. **单案例，且是特例中的特例。** Git 同时具备「无人拥有」与「全民依赖」两个罕见属性。作者没声称可外推，但读者极易外推——这是这类研究的固有风险。
2. **样本偏向大贡献者。** 205 人取自「每季度贡献 80% 以上 commit」的头部。作者补了一个田野观察作补偿：一位排在前 20%、有 12 个 commit 的工程师，自认为不是「真正的」Git 贡献者；而更小的贡献者大概更多是志愿者。这个补偿是诚实的，但**不等于抽样校正**。
3. **「纠缠」这个概念有反噬风险，作者看见了却没完全解决。** 如果一切都纠缠，那么二分化被取消的同时，**批判的抓手也被取消**——「捕获」这个词还能不能用？他的回答是「能，但要分层看」，可这条线划得不够清楚。这是概念工具的通病：解释力越强，指控力越弱。
4. **"real work" 由谁定义，仍然空着。** 作者记录了贡献者的自我命名，但没说明这个命名**如何被制度化、或被驳回**。这恰好是下一步该问的，也是所有「贡献认定」问题的落点。
5. **未见附录与补充材料。** 消歧算法、编码手册、抽样细则、k-means 参数都在附录 A–D 与那份 761 KB 的 docx 里。本文对编码可靠性的评价建立在正文自述之上，没有核到手册一层。
6. **政治经济学的另一半被刻意留白。** 作者把「价值捕获 / 企业控制」与「照护 / real work」并列，但四种逻辑在**冲突时如何裁决**，文中没给机制。这不是疏漏，是这一篇的任务边界。
7. **中国语境完全缺席**（已作为推论在上一节标注）。

## 延伸思考

**一、如果「分离」是观测装置的误差，那我们用什么替它？**

Alcaras 的答案不是取消分类，而是**把分类从「世界」降级为「逻辑」**：不再问「这是公司的还是社区的」，而问「这一段劳动里，价值捕获、企业控制、照护、real work 各占多少，谁在裁决」。这个替换在方法上更强，在**政治上更软**。一个具体的问题：当一位受薪贡献者用公司时间做「小事的工作」，我们还能不能说这是一种「捕获」？反过来——当企业把它当作留人的手段（招安长期志愿者），我们又该怎么称呼它？

我的判断是：**纠缠经济描述的是机制，捕获判断的是权力。** 两者不能互相代替，混用会让分析失去方向感。Alcaras 把这条线留得模糊，这可能是他方法论上最需要后人补的一处。

**二、「没有治理者的治理」是不是一种更危险的状态？**

我们过去把「有边界、有章程、有仲裁」当作治理成熟度的标志。Git 呈现的是相反的情形：**治理有效，但无法定位到治理者**。好处是难以被俘获（没有可以买下的席位），坏处是难以被问责（没有可以对话的对象）。当外部冲击来时——安全问题、许可证争议、AI 生成贡献的洪流——**你找谁谈？** 这与此前观察到的「维护者倦怠被重新定性为国家级攻击的攻击面」是同一问题的两面：**责任需要一个可指认的地址，而自组织恰好不提供地址。**

**三、「理性的梦想」这个概念，值得拿到中文语境里检验。**

Alcaras 说多数志愿贡献者并不做明确职业规划，而是养着一个「理性的梦想」——把 FOSS 当有回报的爱好，等那条晦暗的通道（几乎不出现在招聘启事上、靠私人关系）某天打开。这个描述有个前提：**存在一条通道**。

在产业共同体不承担维持成本、企业不以「养 FOSS 工程师」为常规岗位的地方，这条通道的入口在哪里？如果通道本身不存在，「理性的梦想」就退化为「理性的错觉」。这可能是大分流 2.0 在**动机结构**上最容易被忽略的一层：我们总在比较制度形式（托管平台、许可证、治理章程），却很少比较**职业通路的有无**。而后者才是贡献者用脚投票的真正理由。

**四、AI 那一段留的题，比它给的答案更重要。**

作者问：「1980 年代让自由软件出现的条件，今天还在不在？」这句可以拆成两问：

- **什么东西必须开放，才能让 AI 生产成为集体过程**——数据集、基准、代码还是算力？打开模型本身是可能的，还是必要的？
- **生产链上哪一段可以被公司内部化，哪一段不能？** 那些不能的，才是产业性公共品的候选。

按本文逻辑推下去，最可能的候选未必是模型权重，而是**评估与验证的基础设施**——它像 Git 一样无人拥有、人人依赖、且难以靠单一公司的内部流程替代。这与我们十月里反复遇到的「验证成本是公地稀缺资源」是同一件事的不同入口。**Git 是代码流通的地基，评估集可能是模型流通的地基。** 但按 Alcaras 的框架还得再追一层：这个地基的维持，**由哪个产业共同体承担、按谁的时钟**？

**五、留给适兕的一处反驳。**

这篇最容易被误读成「企业参与开源其实挺好的」或「别再把公司当敌人了」。但它真正说的是：**你连「公司」和「社区」是两回事这件事都还没证明。** 我读下来觉得，对「开源之道」最有用的不是它的结论，而是它对我们话语习惯的**反向校验**：当我说「行政动员造不出生态」时，我是不是也在用一把「真开源在体制之外」的尺子？如果是，这把尺子和 severance 是不是同一把？

我不认为答案必然是「是」——行政动员与产业纠缠在**强制与否**上有实质差别（前者可以不给选择权）。但这个自我校验必须做，否则我们批判的语法会和我们批判的对象共用同一个前提。

> **"I argue that severance, as an unquestioned assumption and methodological convention, prevents us from understanding the entangled economies of digital production."**
> ——「我认为，『分离』作为一种未经检验的假设与方法学惯例，妨碍了我们理解数字生产的纠缠经济。」

> ——「记录互动本身并不能打破『分离』。因为『分离』假设的是：『社区』与『企业』在发生互动之前就已经是两个彼此独立的领域了。」

> ——「（Git 仓库里几乎没有带薪劳动的记录）这个空白并不表明 Git 与产业之间存在天然边界，而是贡献者自己把『敌对世界』的观点表演出来的结果。」

> **"Some knots are uncomfortable, demanding to be undone, sparking open conflict; others are almost seamless and go unnoticed."**
> ——「有些结让人不适，要求被解开，引发公开冲突；另一些几乎无缝，无人注意。」

> ——「企业尽管有战略与资源，仍然难以按自己的意愿控制 FOSS 项目，甚至难以控制自己付钱的那些贡献者。」
