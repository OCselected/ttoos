# 2026-11-22  「开源之道」·论文略读：制度早已就绪，只是在需要它的那一刻没开着

## 论文信息

- **标题**：*A Fine-Grained Empirical Study of Upstream Security Events and Downstream Mitigation in Maven*
- **作者**：Kazi Amit Hasan, Enrong Pan, Yuan Tian, Mariam Guizani, Steven H. H. Ding
- **来源**：arXiv:2610.36603v1 [cs.SE]，2026-10-27 提交
- **原文**：<https://arxiv.org/abs/2610.36603>
- **状态**：预印本，未见刊
- **数据集**：Maven 生态 **832 个 CVE / 257 个上游仓库 / 1,078 个补丁 / 29,952 个下游项目 / 44,450 个 ⟨CVE, 上游, 下游⟩ 三元组**；采纳时间可观测的子集 **1,677 个采纳对 / 742 个下游仓库**

## 一句话推荐

这篇论文把「开源供应链安全」从一场道德问责（「厂商不上心」）改写成一道**时序问题**：洞在上游早就补好了，下游却在等一封没有人发出的信。它最有价值的地方不是样本大，而是让**两组本该互相解释的数字对着看**——上游的沉默与下游的迟到，成因完全不同。

## 内容概要

作者做了一件此前没人逐条做过的事：把每个 CVE 的上游事件链还原成时序。链条上的四个事件——被报告、被修复、被发版、被 NVD 披露——排列组合成六种模式。其中两种最常见：

- **透明修复（T1）**：报告 → 修复 → 发版 → 披露。下游在披露时早就有可用的修复版。
- **沉默修复（S1）**：修复 → 发版 → 披露。**修复和发版都在披露之前完成，但中间什么都没说。**

593 个生命周期完整可观测的 CVE 里，transparent 471 个，silent 361 个。而 **S1 一种模式就占了 silent 组的 81.63%（271/332）**，T1 占 transparent 组的 82.76%（216/261）。

于是最自然的一个假设是：如果上游把修复过程公开（走 T1），下游应该会更早拿到可升级的版本。作者做了卡方检验，结论是——**没有关系**。χ²(1)=0.13，p=0.72，φ=0.01。**报告风格与「修复是否早于披露」无关**，透明修复并不让下游更早拿到可采纳的版本。

真正的落差在下游。1,677 个可观测采纳对里，**1,430 对（85.3%）发生在 NVD 披露之后**；沉默组升到 89.3%；披露后采纳的中位延迟是 **88.1 天**，**42.5% 超过 90 天**。而最刺眼的一行是：**S1 是理论上对下游最友好的模式**（修复和发版都发生在披露前），但 1,012 个 S1 采纳对里有 894 对（88.3%）仍然等到披露之后才动手，中位延迟 86.6 天。它们合计贡献了 **527,119.6 下游-天（1,444.2 项目-年）**的暴露负担，占全部负担的 **63.1%**——最不该出事的模式，贡献了最多的负担。

暴露本身极其集中：**Gini = 0.813，95% CI [0.749, 0.856]**；top 1% 的 CVE 占 38.6% 的暴露，**top 10% 占 72.1%**，top 25% 占 89.0%。

然后是这篇论文最关键的那组数字——自动化能做什么，以及它实际上在做什么。

| 采纳当日 Dependabot 状态 | 采纳对 | 中位「发版→采纳」 | 超过 90 天 |
|---|---|---|---|
| 没有用 | 993（59.2%） | **110.6 天** | 52.9% |
| 有 security update 证据 | 542（32.3%） | **73.2 天** | 46.9% |
| **已配置 version update** | **142（8.5%）** | **10.4 天** | 31.0% |

**110.6 天 → 10.4 天。** 差了一个数量级，代价是一行 `dependabot.yml`。

而在仓库层面，**78.2%（580/742）的仓库「用过」Dependabot**，但到采纳那一天，只有 40.8% 有使用证据、**只有 8.5% 配置了 version update**。先转 security update、后转 version update 的 147 个仓库，中位转换时间是 **585.0 天**——一年半。

最后一组数据把「采纳」这件事的性质彻底改变了：1,677 对里 **41.7%（699 对）的采纳不关联任何 PR 或 issue**；分层抽样的 171 对里**只有 7.0% 在标题或描述中提到 CVE**；bot 开的 PR 采纳中位 **9.0 天，是开发者开的 PR（89.0 天）的十分之一**，而 69 个 bot PR 里只有 7 个提到漏洞。**84.3% 的关联对里，延迟发生在 PR/issue 打开之前**（披露→PR 中位 105.0 天，PR→合并中位 0 天）。`SECURITY.md` 在采纳时的存在率：仅 PR 关联 5.4%，仅 issue 2.8%，两者都有 17.9%，**无关联 1.6%**。

换句话说：**下游绝大多数时候不是在「响应一个漏洞」，而只是碰巧在一次例行更新里把它顺手带过去了。** 那 10.4 天不是安全响应速度，是例行更新的节奏。

## 为什么值得读

因为它测出了制度经济学最难测的那一环。

诺斯反复讲「制度变迁需要有人承担转换成本」，这句话在经验研究里几乎无法落地——你很难找到一个场景，其中转换成本、收益和实际发生率都能同时被观测到。这篇论文给出了一个：

- **转换成本** = 一次性配置 `dependabot.yml`（外加一年半的观望期）
- **收益** = 中位 100 天的暴露时间差
- **实际发生率** = 8.5%

这个交易在任何理性计算下都该做，而 91.5% 的场合没做。**所以阻碍不在交易本身，在于没有人把它当成一笔交易。** 这是「制度已就绪、未采用」最干净的一个计量形态：能力存在率 78.2%，采纳时点生效率 10.9%（8.5/78.2）。

还有一处方法论上的价值，容易被忽略但更通用：**同一仓库在不同日期、面对不同 CVE，上游的披露行为可以完全不同。** 51 个 mixed 仓库（19.84%）承载了 490 个 CVE（58.89%），且 Critical 27 个、High 70 个都在这里。对同一批维护者，一部分 CVE 走沉默、一部分走透明。**这意味着「按仓库研究披露行为」在方法上就是错的，必须按 CVE 研究。** 这是一个会被大量后续研究踩到的坑，作者先把它填了。

## 为什么对开源社区如此重要

**第一，它重新定义了「响应速度」。**

公开讨论供应链安全时，默认的因果链是：上游修 → 下游看到通知 → 下游升级。这篇论文证明这条链的中间环节大面积不存在。82% 的修复早于披露，上游是好样的；下游 88.3% 在披露后才动，看起来是下游懈怠。但再往下看一层，会发现「动」这个动作本身往往与漏洞无关——41.7% 不留任何痕迹，7% 提到 CVE。**所以真正的问题不是「下游不响应」，而是「修复这件事没有被设计成可被响应的信号」。**

上游完全可以做到「修复透明」，同时在发版说明里一字不提。修复的代码是公开的，但「这个版本修了一个洞」这个事实没有进入发版说明——于是发版对下游是一次**零信息动作**。我在素材里给它起了个名字：**沉默发版**。它的判据很硬：*一个下游只用「读 release notes」这一条通道，能不能在披露前知道该升级？* 本案例的答案是：82% 的场合理论上可以，实践中 88.3% 没做到。

这不是谁不负责，而是**发版规范与安全信息的错配**。发版是一个已经制度化的动作，有语义版本号、有 changelog 模板、有 CI 校验；而「这个版本包含一个尚未披露的安全修复」这条信息，恰恰因为披露制度的保密要求，**在时间上无处安放**。

**第二，它给奥斯特罗姆第 4 条（监督）一个极为精确的失效图像。**

Maven 中央仓是一块典型的共享资源池：使用者无排他、维护者分散、单个下游没有维护上游的激励。纸面上的问题是：谁来监督「这个下游项目在采纳时有没有打开自动更新」？

答案是：**没有被授权，也没有人被激励。** 而 GitHub 恰好站在唯一能同时看到上下游、又能读 `dependabot.yml` 的位置上。作者在 §7 的第一条建议，就是让 GitHub 开辟一条**加密的披露前共享通道**——把监督权授予平台上。

这是一个非常典型的「由谁承担监督成本」的答案，也是最容易被质疑的那一类：把治理能力集中到一个私有平台的接口里。它有效，因为位置独特；它脆弱，也因为位置独特。**论文的第一条建议同时是全文最强的洞见和最需要被追问的地方。**

**第三，它让「制度」与「采纳」之间的距离变得可测量。**

威廉姆森四层在这里能一层层落下去：L1（「开源依赖默认可信」这一信任基础）几乎不动；L2（CVE/NVD 披露制度、协调披露规范）——论文证明它**本身工作正常**，82% 的修复早于披露；L3（每个项目的依赖管理治理）；**L4（每个仓库那一行配置）**。

结论刺骨：**L2 的整套制度投入，其效果上限被 L4 的一个开关决定。** 这与此前推荐过的 Kumar 那篇（AI 治理记录的法律沉默被 L4 专有工具填满）方向相反，却同族——那里 L4 是制度的**实际作者**，这里是 L4 的**实际否决者**。同一个层级，两种相反的权力形态。

**第四，它顺带否证了一个流行叙事。**

安全社区长期相信「更透明的上游会让生态更安全」。就「下游能否更早拿到可采纳版本」这一项而言，这篇论文的答案是：**透明与不透明没有差别**。这不意味着透明无价值（它服务于审计、追责、复盘），但它意味着**透明 ≠ 下游会提前行动**。把安全改善押在「让上游更透明」上，本案例不支持。

## 延伸思考

**第一，8.5% 是下界，这让结论变强还是变弱？**

作者自己承认：Dependabot alerts 与仓库安全设置不公开，只能从 PR 与配置文件两个信号反推。所以 8.5% 是**下界**，真实配置率未知。

一般读法会认为这条限制削弱了「制度未采用」的结论。但它其实**削弱的是另一个方向**——如果真实配置率显著高于 8.5%，那么我们就要解释另一件事：为什么配置了却没在采纳日生效？那是一种更麻烦的失效：制度在，但制度的时间管理失序。无论哪种读法，那行配置都没有在需要它的时刻起作用。**所以这条限制不影响论文的核心锋芒，只影响它把责任归给「没做」还是「做了但没在那个时刻」。** 这两种归因对应完全不同的干预方案：一个是激励问题，一个是流程时序问题。作者没有分开讨论，这是论文留下的一道真实的缝。

**第二，如果 bot 比人快十倍，那么治理的默认值在哪里？**

bot 开的 PR 采纳中位 9.0 天，开发者开的 89.0 天——**十倍**。而 69 个 bot PR 里只有 7 个提到漏洞。

这组数字在 AI agent 大规模进入维护流程的今天，意义变得不一样了。当 bot 成为依赖更新的主要执行者，**治理的实际杠杆就从「人的警觉」转移到「bot 的默认值与触发频率」**。而 bot 并不知道什么是安全——它只知道 semver。它的速度来自不看原因地更新。于是我们得到一个非常不古典的公地治理结构：**最快的行动者最不理解行动的意义，而理解意义的人最慢。**

奥斯特罗姆的框架里没有给这种角色留下位置。第 3 条「集体选择安排」预设参与者是人，第 4 条「监督」预设监督者理解被监督的事。当执行的默认值由机器设定，这两条都要重写——而重写的动作不在社区手里，在平台和 bot 作者的默认配置里。

**第三，「时间」这一维度在制度分析中一直缺位。**

诺斯的制度变迁理论主要讲「有没有制度」，威廉姆森讲「成本落在哪一层」，奥斯特罗姆讲「规则是否清晰」。**没有一条主流的制度分析工具问「制度在需要它的那一刻是否处于开着的状态」。**

这篇论文给出的正是这个变量：不是 `是否有能力`，也不是 `是否曾经使用`，而是 `在事件发生的那一刻是否生效`。这个变量一旦被单独计量，很多熟悉的结论都会松动——因为绝大多数「制度有效性」研究用的都是**仓库级、组织级、国家级的静态标签**，而这些标签系统性高估了当时的真实状态（78.2% vs 40.8%）。凡「工具是否在用」类指标，只要工具可开关，就**必须在事件时点分类**，否则量的是历史最大值而不是当时状态。

这个方法论推论可以立刻外推：SBOM 生成率、release attestation 覆盖率、AI 贡献披露标签、OSPO 介入率——全都可以用同一口径重算。**而重算之后，那些漂亮的覆盖率数字大概率会掉一半。** 这不是悲观，而是把「倡议做完」和「倡议生效」分开计量。两者之差，就是倡议本身还没做完的工作量。

**视角：一个视角，不是定论。**

**关键限制**：①采纳时间只对 1,677 对（44,450 个暴露对的 3.8%）可观测，作者明确不假设代表性，所有时间结论均条件于「采纳被观测到」；②Dependabot 隐私型证据不可见，8.5% 是下界；③生命周期日期依赖挖掘时间戳，受时区、延迟打标、历史改写、CVE→commit 错链影响；④以 NVD 发布日期为披露日，而漏洞可能更早公开；⑤单一生态（Maven/CVE 类漏洞），npm、PyPI 及无 CVE 场景不可直接外推；⑥**零中国语境**——中国 Maven 镜像与私有仓下的采纳行为未涉及，故本文不做「大分流 2.0」延伸。预印本未见刊，未经同行评审。
