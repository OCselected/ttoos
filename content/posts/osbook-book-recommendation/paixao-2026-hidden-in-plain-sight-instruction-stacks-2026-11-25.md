## 一句话推荐

题目起得比内容还准：**归属规则就明明白白写在请求里，只是没有人被要求去看它。** 「谁算贡献者」这件开源世界里最要紧的事，此刻有一条规则正躺在某个厂商的工具描述文本里，可以抓包拿到，可以由厂商在下一次发版时单方改掉，可能没有 PR、没有理由、没有版本史。

## 内容概要

论文要做的事很简单，也很难：把编码 agent 每次真正发给模型的文本抓下来，看看里面到底装了什么。方法是受控沙箱里对每个版本发起一次「首次请求」，剔除用户 prompt 与 API 参数，只留**指令栈**（instruction text + tool definitions），然后做两件事——静态看组成，动态看变化。

**组成：用户的输入几乎不存在。** Claude Code 2.1.243 的首次请求共 74,078 字符，其中 `tools` 字段 57,346 字符（20 个工具定义）、`system` 9,517 字符，而用户的 prompt 是 21 个字符——**0.03%**。最新版本里工具定义的占比：Claude Code 77.4%、Qwen Code 72.3%、OpenCode 63.2%、Codex 40.5%、Gemini CLI 18.9%。Claude Code 的工具描述总长是指令文本的 2.6 倍，而其中一个 `Workflow` 工具**单条描述 19,290 字符，比整个 system prompt 还长**。

在对指令文本的分类里，directive 类占到中位的 89%–96%（communication / engineering / tool guidance 合计 73%–78%），而**执行策略（权限与不可逆操作）只占 2%–6%**。也就是说，这些被写进去的绝大部分文本，讲的是「你怎么写代码、怎么说话」，而不是「你不许做什么」。

**变化：不频繁，但成串发生，且「加了又删」的量是净增长的 13 倍。** 1,867 个可测 transition 中只有 544 个（29%）真正改了某段或某个工具，改动的 median relative edit size 仅 0.6%–2.0%。但每个 agent 有**一半的累计编辑量集中在 5–10 个 transition** 里。全样本新增 3,108 段、删除 2,751 段，而修改仅 537 段；字符上新增 306,176、删除 263,685，**净增只有 42,491**——13:1 的重写比。最极端的一例是 Claude Code 2.1.69 用单个 `ToolSearch` 工具替换 18 个工具定义，请求从 77,601 字符降到 20,380，**次日 2.1.70 全部恢复**。

**归属：规则在工具描述里，而且被改过。** 493 次 Claude Code 抓取中，有 **492 次**的 `Bash` 工具描述要求模型追加 `Co-Authored-By: Claude`——这正是 AIDev 数据集用来识别 Claude Code PR 的那个标记。OpenCode 在 907 次抓取中有 312 次含同类指令，**0.4.20 版（2025 年 8 月）移除**。其余三个 agent 的栈里**没有任何归属标记**。论文还记录了注释策略的 5 次改写：最严的 `DO NOT ADD ***ANY*** COMMENTS unless asked` 出现于 186 of 493，**2.1.154 起改为「match its comment density」**。

**理由：不到一半。** 496 个 change unit 里 444 个（90%）陈述了某种理由，但**只有 236 个（48%）说明的是指令栈本身为什么改**；208 个（42%）只解释了随之而来的代码改动。无 PR 的 commit 最差：56 个里 21 个（38%）完全不说理由，而有 PR 的 440 个里只有 31 个（7%）。动机分布上，model behavior 150、new capability 127、maintenance 102，而 **safety 只有 13 个**——即使改动的是权限与不可逆操作，24 个有理由的 unit 里也只有 2 个提到安全。

## 为什么值得读

- **它把「归属是谁定的」这个问题从抽象拉到了字符级。** 我们这半年反复讨论「agent 贡献算不算贡献」，默认前提是「有人在做这个判断」。这篇指出：在某些链条上，做判断的是一段厂商可以随时重写的自然语言。
- **它给出一条可直接复算的证据链，从版本号到 PR 到 commit 到理由。** 496 个 change unit 的溯源，是本季实证研究里少见的「每个结论都能倒着走回去」的构造。
- **它顺手证明了「看净变化」这种最常用的度量方式在这里完全失效。** 净增 42,491 字符听起来微乎其微，而实际发生的重写量是它的 13 倍。所有用文件 diff 大小衡量规则变更强度的 dashboard，都踩在这条陷阱上。

## 为什么对开源社区如此重要

先把它与本站此前几篇放在一起：一篇研究「去掉署名后能否识别 agent 提交」（783 万次提交，真实占比下 precision 仅 0.332，换一个 agent 即崩溃），还有关于 PR 凭证形态变化、供应链事件归因的研究。三篇合起来指向同一处结构：**事后识别不可行，上游来源不可追溯，披露字段不可依赖。** 这篇站在更上游——它问的不是「怎么认出来」，而是「那条规则是谁写的、写在哪、改的时候有没有人知道」。

从制度经济学读，有三层。

**第一层：规则的存放位置决定了它的可问责性。** 开源世界里任何一处行为变更——API、许可证、CONTRIBUTING——都被要求留痕，理由是「无人可查的变更等于无主授权」。而这批编码 agent 的「贡献标注规则」处在一个完全不同的位置：它藏在工具描述的自然语言里，由厂商单方改写，改动可能没有 PR、没有理由、没有版本史。Claude Code 是闭源的，在 1,393 个开源 agent 版本、1,886 个请求中，唯独它无法追溯到 commit。**这意味着：被记录的对象的标注方式，由记录工具的生产者决定，而被记录方与记录方都不一定知道它什么时候变过。**

**第二层：可问责性需要一个前提，就是行为规范本身可审。** 这里有 48% 这个数。把它当「贡献者」看待是有代价的：贡献者的前提是行为可被问责，而一个只有不到一半变更能给出理由的实体，在责任链条上是一个洞。更麻烦的是这个洞的位置——它不是缺证据，而是**没有人被要求提供证据**。

**第三层，也是这篇最锋利的地方：这是治理的第四种失效形态。** 这些文本是公开的，抓包就能拿到，大多还躺在开源仓库里。失效不是因为保密，而是因为**没有任何制度要求它被呈现、被比对、被记录**。本站此前记录过三种并列形态：制度沉默（法规不说用什么格式，于是默认值填满）、制度词义被改（一个副词被删，义务性质随之改变）、制度从不可争（无草稿版本史）。这一篇补上第四种：**制度公开但无人被要求阅读它。** 由此得到一条新的桥接概念——**可获取性不等于可审性**（availability is not auditability）。判据不是「文本拿不拿得到」，而是「有没有制度要求某方在变更时，留下一份能被第三方比对的版本史与理由」。本案例把三者分得很清：文本 100% 可获取、48% 有理由、闭源者 0% 可追溯 commit。

还有一层是方向。威廉姆森的四层框架里，厂商的一次默认值改动属于最底层的资源配置动作，而下游社区「用什么方式认定 agent 贡献」属于治理机制层。通常我们担心的是上层约束不了下层，这里是**下层直接改写上层**：一次发版，社区的贡献认定口径就变了。作者的处方恰好是逆着这条传导链往回装一道闸——*the agent release should be part of the experimental configuration*，以及发布时应同时公开抓取的指令栈并保留修改理由。这个处方非常「开源」：**不要求公开源码，要求公开「影响行为的那份文本」与「为什么改」。** 它和此前记录过的「最小可复核集」（格式 + 一份实现 + 测试向量）同构，AI 时代的版本是：**指令栈 + 版本号 + 修改理由**，三件缺一不可。

最后记一条更便宜的分析工具。论文量化出一个反直觉的分布：**「模型行为」类的动机 146 of 150 都直接解释了指令为什么改，而新功能 114 of 127、维护 83 of 102 只解释代码。** 换言之，开发者只在自己「引导模型」时才解释指令，其余时候规则是搭着代码一起变的。由此得到第二条桥接概念——**搭车变更**（piggybacked change）。它的制度含义很值得记：**规则变更的可解释率，与它是否被视为「规则」成正比。** 被当成规则的会写理由，被当成代码的不会。这是判断一个系统里「什么算制度、什么不算」最便宜的探针——不看文档写没写，看改动的人有没有觉得需要解释。

## 延伸思考

**第一问：如果这条规则可以单方改写，那「贡献者」这个身份还剩多少自主权？**

开源世界的功绩制建立在一个前提上：贡献的认定标准由社区自己写、自己改、自己解释。而当「怎么标注一条 AI 辅助提交」由工具厂商在自己的发行节奏里决定，社区连「什么时候变的」都不一定知道。这不是谁在恶意操纵——恰恰相反，厂商多半只是在改进工具。问题在于**位置**：一个不在社区治理结构里的主体，握有一项对社区治理有直接效果的权力，且这项权力的行使不需要向社区披露。用威廉姆森的话说，这是治理结构与交易属性不匹配；用更朴素的话说，**决定权跟着分发入口走了。**

**第二问：把「48% 有理由」当成批评厂商，公道吗？**

不太公道，值得说清楚。48% 是基于 stated motivations 的统计，不等于真实动机缺失——作者自己在 Threats 里承认，开发者可能省略或误述。更公道的问题是：**为什么没有人被要求留下理由？** 一个把「改 API 要写 changelog」当成基本职业素养的行业，在改动一份会直接塑造数百万行代码生成行为的文本时，却没有对应的惯例。这不是某家公司的品格问题，是一个缺口还没被人画上边界。

**第三问：如果规则变更的可解释率真的与「是否被视为规则」成正比，这是不是一条可用的诊断法？**

这是本篇最被我记下的一条。它的操作性极强：想知道一个团队、一个项目、一个平台把什么当真制度，不必读它的治理文档，只需看它在改什么的时候会主动写理由。写得出的，是规则；写不出的，是代码——不管它被放在了什么文件名底下。这条规律对开源项目自身同样成立：如果某个项目的治理文件一年改三次、三次都没有理由，那它和这篇论文批评的对象，区别只在写得公开一点。

**第四问：这篇论文自己的边界，正好是治理无法跨越的那段距离。**

作者写得很实在：抓取止于 2026-08-25，只抓首次请求、空工作目录、无用户交互、固定配置；动机分析只覆盖 4 个开源 agent，**Claude Code 因闭源被排除在 RQ3 之外——而它恰是归属性问题最相关的那一个。** 另有 15 个 OpenCode 版本无法初始化 provider、7 个包损坏，最终样本是 1,886/1,911。我未复跑抓包，所有栈组成与变化数字采信原文。这些限制里最要紧的是第一条：**指令栈的结论有保鲜期**，而这条链恰好是变化最快的软件品类之一。

**最后一条必须声明：本篇零中国语境。** AtomGit、Gitee、OpenAtom 上的编码 agent 指令栈不在样本内，国内 agent 的默认配置未涉及。把这里的结论平移过去之前，得先回答一个本文没问的问题：**在这些平台上，agent 的归属标注是默认开启还是默认关闭？** 一个默认值的方向，就足以让整张图变成另一张。
