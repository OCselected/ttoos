## 一、今日核心命题：开源社会契约的集体重新协商

10-08 是「AI 冲击开源公共基础设施」（Katz 论文的 Stack Overflow 命题），10-09 是「外部脆弱性的多层化」（Yongjie Han 气候层 + Docsy 文档基础设施 LF 化 + LF Europe 贡献度-治理权断层）。今日的命题在 10-08 的「冲击」命题和 10-09 的「多层化」命题之上再走一步——**开源社会契约的集体重新协商已经开始，且以三种不同的方式同时发生**：

- **上游层**（jross）：**贡献审查机制本身**变得不可持续，主流项目集体转向封禁外部 PR；
- **资金层**（DigitalOcean）：**入门级云额度资助**被撤销，FOSS 项目失去一类入门级资源入口；
- **技术层**（OpenTPU）：**agent 自己设计自己运行的硬件**——开源方法论的第一次递归自我改进样本。

三条路径合起来，把开源社会契约的三次结构性压力（贡献、资金、技术）在同一个观察窗口里暴露——**「开源之道」命题的 Agent 时代版本必须同时回应三个问题**：谁贡献、谁资助、谁设计。

## 二、思想层：开源社会契约崩塌命题的公开表达

### 📖 1. Open Source as We Know It Is Dead（jross, 2026-10-05, **本日核心样本**）

- **来源**：[jross.me](https://jross.me)（HN 102 pts + 64 评论，2026-10-05）
- **原文命题**：AI 生成 PR 使「贡献审查」成本不可持续，主流开源项目集体转向封禁外部 PR——tldraw、Ghostty、Jazzband（整体关停）、OpenJDK、Ladybird、Godot、COSMIC、Codeberg（投票禁 AI 项目）、Sindre Sorhus（个人仓库全线关闭）。

**具体制度安排（贡献机制层）**：

| 维度 | 制度安排 |
|------|---------|
| **发布主体** | GitHub（2026-02 官方博文《Welcome to the Eternal September of open source》）+ 上游项目维护者 |
| **规则要求** | GitHub 推出「用户级 PR 上限」「外部 PR 关闭」「AI agent 计入 PR 配额」等特性；上游项目把 AI 生成 PR 从「社区贡献」中隔离 |
| **谁被纳入/排除** | 独立贡献者、AI agent、AI 辅助贡献者被系统性地排除在贡献渠道之外 |
| **资源分配** | 审查者时间预算被外部压力耗尽——不是「不想收」，是「没有能力收」 |
| **协作行为影响** | 上游开源项目的「外部贡献入口」正在关闭，开源从「bazaar 隐喻」（大量贡献者自发协作）向「cathedral 隐喻」（少数核心团队 + 严格过滤）退化 |

**「开源之道」点评（Williamson L1 社会嵌入层的核心命题）**：

- **Coase 1937《企业的性质》命题在开源协作场景的第六次精确化**——前五次在「AI 合规外包」「AI 治理架构」「AI 治理工具的可复核性」「数字公地的消费者边界」「开发者的生理嵌入」；这一次是「贡献审查作为开源协作的最终瓶颈」。**Coase 问「企业为什么存在」，本质是问「交易成本高的时候把协作内部化有多便宜」——开源社会契约的崩塌命题本质上是问「贡献审查成本过高时，把开源内部化的边界画在哪里」**。
- **Ostrom 1990 八原则在开源场景的最新失败样本**——Ostrom 讨论「公地治理如何成功」，隐含假设是「公地治理是可承担的」。贡献审查成本外溢之后，第 5 条「监督」「第 7 条「低成本冲突解决」全部失效。**Ostrom 意义上的开源协作公地已经不再满足「可承担的治理成本」这个前提条件**。
- **Lerner-Tirole 2002 声誉机制的当代版本失效**——Lerner-Tirole 假设「贡献者通过开源贡献获得声誉资本」。当 AI 让「贡献」变得廉价而「审查」变得昂贵，声誉机制的经济学基础崩塌——贡献不再是稀缺品，审查才是稀缺品。
- **Benkler 2006 网络众包命题的第二个失效样本**（第一个是 Katz 10-08 的消费者端失效，本次是**贡献者端失效**）——Benkler 假设「贡献与消费在开源生态内是连贯的、连续的」，本文揭示贡献端和消费端都在结构性崩塌。

**未来检验点**：
- ①GitHub 上「PR closed by default」设置的项目数增长曲线；
- ②Codeberg 上「AI 项目拒收」投票的实际执行率；
- ③Forgejo / Gitea 自托管实例的迁移趋势——如果主流项目集体关闭外部 PR，自托管的开源协作平台（Forgejo、GitLab CE）可能反过来成为主要承载地。

**误判风险**：这一命题可能被过度政治化；作者本人在文末承认「不知道解决方案」。作为**观察信号**保留，不预设终局判断——是否真的进入「开源社会契约崩塌」阶段，需要至少 6-12 个月的观察窗口。

### 📄 2. （外围）Open Source AI, Open Liability AI（Bryan H. Choi, SSRN 2026）

- **DOI**：[10.2139/ssrn.6339098](https://doi.org/10.2139/ssrn.6339098)
- **核心命题**：开源 AI 不应享有传统慈善豁免式的责任豁免；主张引入普通侵权法上的**注意义务**（duty of care）。

**制度层分析**：把「开源」作为责任豁免的借口是一种**慈善豁免理论的挪用**——开源的公共性不等于法律特权。这是把开源从「协作方式」重新拉回「制度约束」的规范性讨论，与 10-06 收录的 Kumar（「AI 治理工具应开源」）构成镜像对照：**开源治理工具应开放以保公共可复核性** ↔ **开源 AI 的责任不应豁免于公共可问责性**。

**收录理由**：作为「开源责任豁免边界」命题的最新工作论文**外围收录**——今日核心命题是「协作机制」，责任豁免边界是「协作机制」的镜像版本（谁有权被免责）。

## 三、资金与资助层：开源俱乐部品 vs 公共品边界的商业重划

### 💰 1. DigitalOcean 关停 Open Source Credits Program（**本日核心样本**）

- **来源**：[It's FOSS, 2026-10-05](https://itsfoss.com/news/digitalocean-open-source-credits-end/)（HN 49 pts）
- **摘要**：DigitalOcean 结束其开源云额度项目——原为 FOSS 项目提供 $60–$20,000/年的云资源额度，按 GitHub stars 和 OSI 许可证分档（Testing / Staging / Production 三档），改为统一的 DigitalOcean Startups Program。

**具体制度安排（资助机制层）**：

| 维度 | 制度安排 |
|------|---------|
| **发布主体** | DigitalOcean（商业云厂商） |
| **规则要求** | 资助条件从「GitHub stars + OSI 许可证」（开源度量）切换到「Startups Program」（商业启动度量） |
| **谁被纳入/排除** | 中低 stars 的 FOSS 项目失去「入门级云额度入口」；stars 高、社区活跃的开源项目基本不受影响 |
| **资源如何分配** | 资助从「按开源指标分配」变为「按商业潜力分配」——公共性指标被商业指标替换 |
| **协作行为影响** | 开源生态的「入门级资助通道」减少一条——新项目的启动成本上升，「开源俱乐部品」门槛被商业逻辑重划 |

**「开源之道」点评（适兕「开源俱乐部品 vs 公共品」命题的最新样本）**：

- **credit 项目本质是「俱乐部品门槛」而不是「公共品分发」**——公共品的定义是「非排他、非竞争」，但 GitHub stars + OSI 许可证分档明确地**排他**（低 stars 被排除）、**竞争**（stars 是零和的注意力经济）。过去把这类 credit 项目归入「公共品」是概念误用；它一直是俱乐部品。
- **关停不是「DigitalOcean 一家的事」，而是「云厂商用 credit 换生态」的资助逻辑在被重新定价**——同样的机制正在其他云厂商内部被讨论。这是「资助制度层面」的一次观察信号。
- **与 IvorySQL 类的「Good First Issue 激励扭曲」机制同构**——把「社区活力」量化为 stars 是一种激励扭曲装置：stars 是关注度的代理指标，不是贡献质量的代理指标。**过去 credit 项目在鼓励项目追求 stars 增长（而不是追求贡献质量），这是一种隐性的制度扭曲**。关停之后，中低 stars 项目失去的不仅是资源入口，还有「被鼓励追求 stars 增长」这个扭曲的激励装置。
- **Coase 交易成本的新变量**：过去开源项目获取云资源的「交易成本」是「申请 + 审核 + stars 门槛」；关停之后变成「无入口」。**交易成本从「高」跳到「∞」是一种制度性变化**，不是渐进的。

**未来测试**：
- 关停后 6-12 个月内，中等规模开源项目（500–5000 stars）的自建基础设施支出上升曲线；
- 其他云厂商（AWS、GCP、Scaleway、Hetzner）是否会跟进关闭或调整 credit 项目；
- 是否会出现替代性的「按非商业指标」资助机制（比如 Gitcoin Grants、Open Collective、社区众筹）作为「公共品资助」的替代品。

**误判风险**：把「关停 = 商业厂商抛弃开源」是过度简化——DigitalOcean 的商业决策有它的商业逻辑，与「是否亲开源」无关。真正的观察点是**「按开源指标资助」这条路径在商业云厂商内部正在被重新定价**，不是「厂商抛弃开源」。

## 四、技术层：agent 时代的开源方法论极端样本

### 🔬 1. OpenTPU：AI 自动设计的开源 AI 加速器（**本日核心样本**）

- **来源**：[github.com/FeSens/openTPU](https://github.com/FeSens/openTPU)（Apache 2.0, HN 345 pts / 401 评论 / 2026-10-06）
- **摘要**：整个 AI 加速器（RTL、ISA、bit-exact simulator、编译器、profiler）在**一个 monorepo 内由 AI agent 迭代设计**。在 Kintex-7 PCIe 卡上跑 Qwen3、Qwen3.5、Gemma 4、Phi-4-mini 等真实权重模型，LFM2.5-230M 达 85.8 tok/s。作者方法来自 auto-arch-tournament（AI 设计 RISC-V 核心）。

**具体制度安排（技术方法论层）**：

| 维度 | 制度安排 |
|------|---------|
| **发布主体** | 单一作者 / 小团队（FeSens），Apache 2.0 |
| **规则要求** | RTL + ISA + simulator + 编译器 + profiler 全部在一个 monorepo 内由 AI agent 迭代生成 |
| **谁被纳入/排除** | 任何愿意运行 Kintex-7 PCIe 卡的开源社区成员可复现 |
| **资源如何分配** | 算力成本从「硅片厂 + FPGA 团队」转移到「agent + FPGA」——设计权从「硬件团队」转移到「agent 调度系统」 |
| **协作行为影响** | 「谁能写代码」和「谁能写硬件」的边界正在消融——开源的价值从「共享源代码」变成「共享可验证的完整工具链」 |

**「开源之道」点评（Williamson L4 资源配置层的第一次硬件开源样本）**：

- **Coase 交易成本的极限形式**——如果 AI agent 可以自动设计一个能跑自己的 chip，那么「谁能写硬件」这个过去被认为需要数亿美元 + 数年的资本投入的边界，被 agent 调度系统一次性打破。**交易成本从「10 亿级」降到「单人 6 个月」是开源历史级别的下降**。
- **Williamson L4 层面的资源配置正在被 AI agent 重新定价**——过去讨论 agent 治理聚焦在「软件协作层」，本文首次把它推到「硬件设计层」；开源四层制度基础设施从「L1-L4 都是软件协作」扩展为「L4 可以包含硬件设计」。
- **与 10-08 收录的 Katz 论文构成对照**——Katz 讨论「AI 让贡献变难」（贡献端失效），本文讨论「AI 让设计变易」（设计端突破）。**两个方向同时发生**——开源协作的入口层在关闭（贡献审查不可持续），但入口层的下游（技术设计能力）在被 agent 打开。
- **制度缺口**：开源硬件的知识产权边界（RTL 的 patent vs license）远比开源软件复杂——Apache 2.0 覆盖的是源代码授权，但 RTL 可能同时涉及硬件专利、EDA 工具专利、IP 核专利。**目前尚无成型的开源硬件知识产权规范**。

**未来测试**：
- OpenTPU 的 RTL 是否被独立第三方验证（可复现性）；
- 是否会出现开源硬件的知识产权规范（比如 Apache Hardware License、OHL 更新）；
- 其他 AI agent 是否会在 auto-arch-tournament 的开源上做出第二个类似的样本。

**误判风险**：本文的「agent 自动设计」叙事可能过度简化——实际工程流程中，作者仍然做了架构设计、决策、迭代方向的选择。作为「AI agent 时代开源方法论的一个激进样本」观察，不作为「agent 完全替代工程师」的证据。

### 🤖 2. AWS Strands Decider 2B：agent 时代的模型分层信号（外围观察）

- **来源**：[strandsagents.com/blog/introducing-strands-decider](https://strandsagents.com/blog/introducing-strands-decider/)（HN 284 pts / 78 评论）/ [github.com/strands-labs/strands-decider](https://github.com/strands-labs/strands-decider)
- **摘要**：2B 参数的小型「决策模型」——不是生成文本的 LLM，而是对给定 state + question 输出 yes/no 或 N 选 1 的**分类/置信度打分模型**。v19 版本对图像训练 2B decider 达到同等精度，但在 NaturalBench 上的校准显著更好（ECE 0.014 vs 0.080）。

**「开源之道」点评（Coase 交易成本的边界重估）**：

- **Coase 1937《企业的性质》命题的当代版本**——如果决策可以用 2B 模型完成，就不必调 LLM，这本身就是交易成本的重估。**过去 agent 时代把「每一次决策」都视为「一次 LLM 调用」，本文揭示的是「决策可以按规模分层」——2B 决策模型 vs LLM 是两种不同的治理机制，对应不同的交易成本结构**。
- **与 10-06 收录的 Agent Labor Piece-Rate 论文构成对话**——「agent 劳动力」这个概念过去被假定为「LLM 调用」，本文揭示「agent 劳动力」可以是「2B 决策模型调用」。**agent 时代的经济学建模需要区分「生成式劳动力」和「决策式劳动力」两种形态**。

**收录理由**：**agent 时代的模型分层信号**——外围收录，作为「开源基础设施层边界扩展」的观察样本（Apache 2.0 + 可本地部署 = 基础设施级开源）。

## 五、治理机制层：基金化 vs 独立社区路径的实证对照

### 📊 1. vLLM v0.31.0 vs SGLang：治理路径的实证对照（**制度健康观察**）

- **vLLM 时间线**：v0.31.0 (2026-10-05) / v0.30.0 (09-22) / v0.29.0 (09-09) / v0.28.0 (08-26) / v0.27.1 (08-11)——**稳定 12–14 天/版本**。
- **vLLM 治理**：2025 年 4 月正式加入 LF AI & Data 基金会（v0.10.0 之后）。
- **SGLang 对照**：保持独立治理，每两周一个 minor 版本，速度更快但 maintainer 集中。

**制度层分析（Acemoglu 包容性 vs 汲取性）**：

- **基金化让 vLLM 更接近「制度性协作」**——release 流程标准化、review 门槛提高、maintainer 治理路径制度化。
- **独立治理让 SGLang 更接近「社区自发秩序」**——maintainer 决策更集中、迭代节奏更快、无基金会治理层的约束。
- **两条路径在开源世界的合法性都需要被承认**——Acemoglu 的「包容性 vs 汲取性」在这里没有简单优劣。

**开源之道判断**：这是**「慢聚漫奏（求兴）vs 效率求生（大分流 2.0）」在推理框架领域的现实对照**——vLLM 的路径更接近「求兴」，SGLang 的路径更接近「求生」。**过去讨论大分流 2.0 都在说「中国走求生路径」，本文揭示的是「美国内部也有求兴路径」（vLLM），美国开源世界的两条路径共存**——大分流 2.0 命题需要重新审视「制度差异 vs 制度共性」的双维度。

**观察窗口**：vLLM 加入 LF AI & Data 后 12 个月内，maintainer 决策权结构如何演化；SGLang 是否会在某个时间点基金化。
