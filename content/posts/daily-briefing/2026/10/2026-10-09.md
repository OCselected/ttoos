## 二、论文与思想层：气候冲击开源协作网络

### 🌡️ 1. Too Hot to Commit? Extreme Heat, Developer Output, and Collaboration Networks in Open-Source Software（**核心样本**）

- **作者**：Yongjie Han（SSRN，2026-10-08 上线）
- **DOI**：[10.2139/ssrn.7582038](https://doi.org/10.2139/ssrn.7582038)
- **数据**：739,587 名活跃 GitHub 用户的日级 commit 面板 + 每人每天最高气温

**核心发现（两条）**：

1. **极端高温显著降低个体 commits 产出，且后续几天几乎没有恢复**。这是「远程高技能数字劳动」的物理外部性第一次被面板数据严肃量化——过去讨论开源可持续性都在制度层（治理结构、贡献激励、许可证），本文把它放到物理环境层（气候冲击）。
2. **地理距离较远的协作对中，一方产出下降与另一方产出上升相关**——即协作网络提供了某种「地理风险分散」的补偿机制。

**「开源之道」点评（制度层分析）**：

- **Coase 问题在开源层面的极端变形**：Coase 问「企业为什么存在」（内部交易成本 vs 外部交易成本），本文反过来问「如果开发者的生理状态是外部交易成本的一部分，那么协作网络的地理分布如何内化这个成本」。
- **Ostrom 公共品框架从生态域移动到数字域**：Ostrom 的公共品讨论原本就包含「生态公共品」（渔场、林地）的脆弱性分析，本文追问同一个问题——「当共同体的边界跨越地理和气候带时，物理冲击如何影响协作产出？」
- **Williamson L1 的最底层嵌入性**：气候嵌入性比「社区文化」更基础——它直接影响开发者的生理状态，是社会嵌入性 L1 的物理底层。
- **自发秩序的具体样本**：作者的第二个发现（远距协作对中一方下降、另一方上升）暗示开源协作网络的**天然抗风险属性**——不是治理设计出来的，是分布产生的。这是哈耶克意义上的 emergent order 在开源协作中的一个具体样本：**气候冲击被网络结构自发分散，无需任何中心化治理安排**。

**观察问题（未来测试）**：
- 论文是否控制了「远程工作者 vs 办公室工作者」的比例？如果气候冲击主要影响办公室工作者，那么发现 2 可能只是「地理分散」而非「风险分散」。
- 中国/印度气候带的贡献者群体在极端高温事件下的产出曲线是否有区域差异？
- 作者未讨论「空调基础设施」如何中介气候→产出的传递路径——这是制度基础设施与物理冲击的交互项。

**误判风险**：把「远距协作的风险分散」解读为「开源网络天然抗风险」是过度外推——需要区分「地理分布带来的独立冲击分散」和「主动治理设计带来的抗风险能力」，两者不能混同。

## 三、产业与政策动态：LF 的「文档基础设施化」

### 📄 1. Google Docsy 项目加入 Linux Foundation（**制度健康正向变化**）

- **来源**：The New Stack，2026-10-08
- **切入角度**：「AI agents 正在成为文档的读者」——当 agent 大量读取文档时，文档的**语义互操作性**变得像 API 一样重要，因此把 Docsy 放到中立基金会下治理。

**具体制度安排**：

| 维度 | 制度安排 |
|------|---------|
| **发布主体** | Linux Foundation（美国非营利基金会） |
| **规则要求** | Docsy 从 Google 单公司项目 → LF 中立治理；技术决策权从 Google 单一决策者扩展到 LF 下的多方成员 |
| **谁被纳入/排除** | 任何使用 Docsy 生成文档的组织；LF 会员获得治理席位 |
| **资源分配** | Google 保留项目主导权，通过 LF 让第三方维护者与用户获得「制度性发言权」 |
| **协作行为影响** | 治理权从「厂商单点」扩展到「跨公司中立治理」——**文档基础设施层的第一次 LF 化事件** |

**关键判断（Williamson L2→L3）**：

- 过去 LF 治理的是**运行时层**（Linux）、**云原生层**（CNCF）、**AI 层**（PyTorch Foundation、AAIF）。Docsy 属于**文档层**——即「agent 读取人类产出知识的入口层」。LF 从「运行时基金会」进入「知识基础设施基金会」的判断**可能成立**，但需要一个观察窗口。
- **观察问题（关键）**：Docsy 项目的 TC（Technical Committee）成员构成会否延续「Google 主导」？
  - 如果延续 → LF 化只是**外部治理**（多厂商会员）而非**内部治理**（多厂商决策权）；
  - 如果引入非 Google 主导 → 则「LF 从运行时进入知识基础设施」的判断成立。
- **判断标准**：制度环境（LF 中立治理）与治理机制（Docsy TC 结构）之间的转化效率，决定 Docsy 是「制度性开源」还是「技术性开源」。

**未来测试**：跟踪 Docsy 首次 TC 会议时间、TC 成员公告、非 Google 主导者的加入时机。
