## 「开源之道」 2026-11-22 搜集事件和材料

> 今天三篇论文看似分散，其实各戳同一个转变的不同侧面：**开源最值钱的东西正在从「代码产出」变成「能力的可继承性」。**
>
> ① **第一篇把话说得最直接。** 高能物理的软件训练正在从「代码生产」转向「科学管护」，因为生成式与 agentic AI 削弱了「产出一个成功的计算产物」与「对该产物所依赖的关键选择保持科学掌握」之间的联结。它给了一个否决式定义：**能力不看能不能写出来，看能不能为结果提供证据**。
>
> ② **第二篇用热力学语言给编码 agent 记账。** 一次成功运行里，**约 80% 的 token 花在对最终变更毫无影响的调用上**；真正推动变更的自由能只占 14–22%。这不是道德问题，是搜索过程的熵——噪音的结构性原因被算出来了。
>
> ③ **第三篇把 agent 放进组织里测。** 101 个任务、26 位模拟同事，最强的两个模型满足约 63% 的 fail-to-pass 测试，却完成不到 8% 的完整任务；93% 的首次提问找对了负责人，但只拿到 64% 的同事持有需求。**找对人是路由，拿到需求是承诺。**
>
> ④ **新闻面三件事都在回答同一个问题：一个组织怎么把「能力」变成「可继承的制度」。** LLVM 用八年重许可写下终止判据；OpenSSL 用十年四步走到标准组织的席位；Google 把 agent 的执行层交给 CNCF，保留模型层。Project Pulse 深看的 Django 则把这个问题的答案写成了硬规则：**Mergers 不得少于三人**。

#### 1. 「产出成功」与「保留判断」之间那道被 AI 削薄的联结

**Training for sustainable scientific software in the AI era: from code production to scientific stewardship** · Juliette Alimena（单作者）（arXiv:2611.23330，cs.SE / hep-ex，2026-11-16）

**链接**：[arXiv:2611.23330](https://arxiv.org/abs/2611.23330)｜DOI [10.48550/arXiv.2611.23330](https://doi.org/10.48550/arXiv.2611.23330)

**摘要**：作者从高能物理（HEP）的软件实践出发，提出一个**概念性论断而非实证**：生成式与 agentic AI 改变了研究者与科学软件的互动方式，其生产率效应因任务与人而异，但**它们会削弱「产出一个成功的计算产物」与「对该产物所依赖的关键选择与证据保持科学上的掌控」之间的联结**。因此 HEP 的部分训练挑战从「代码生产」移向「科学管护（stewardship）」——研究者必须能够验证、解释、复现、维护并为部分由 AI 生成或修改的软件与工作流提供理由。作者主张 AI 时代软件训练应双轨：既教 AI 系统本身，也把 AI 嵌入既有的软件与分析训练中；**测试、溯源（provenance）、可复现性、资源判断、科学验证**必须在 AI 辅助的工作流里被实际操练，且**能力应以「支持某个结果的证据」而非「能否生成代码」来评判**。她把这件事框定为「可持续科学软件」问题：AI 辅助的工作流应当保持可信任与可维护、负责地使用算力，并避免让核心能力不必要地依赖于对特定工具与基础设施的特权访问。

**为什么与「开源之道」相关**：这是本周唯一一篇把「AI 改变了什么」落在**存量能力**而非增量产出上的文章。它最有价值的一句是那句否决式定义——能力不看「能不能写出来」，而看「能不能为结果提供证据」。这个判据平移进开源不需要任何改动：一个 PR 的价值从来不在于 diff 是否存在，而在于它背后有没有测试、有没有溯源、有没有人在合并后仍能解释它为什么在那里。

**「开源之道」点评**：真正锋利的是最后那半句——「避免让核心能力不必要地依赖对特定工具与基础设施的特权访问」。这句话在科学语境里说的是别让科研能力绑死在某个商业 API 上；但在开源语境里它同时是**「公地」与「特许工程」的分界线**。当一个学科的核心能力只能通过某个闭源工具获得时，它名义上还在做科学，制度上已经退回了行会。开源之所以值得作为一种制度来谈，恰恰因为它要求的是**能力可以在任何有算力的地方被重新长出**——而不是能力可以随时被租用。

要克制的两点。第一，这是**立场文章，不是实证研究**：没有样本、没有测量、没有对照，全部论证是概念推演 + 学科经验。引用它的时候不能把它当成「有证据表明」。第二，它的场景（HEP）异常特殊——高度协作、代码生命周期以十年计、有成熟的数据与软件复用文化。在这个场景里「stewardship」是自然语言，但在一个由单人维护的 npm 包上，同样的话会立刻变成一句不合时宜的道德要求。**制度分析要小心：不要把一个有余裕的学科的能力标准，直接搬去做多数开源项目的考核标准。**

#### 2. 八成 token 是热：给编码 agent 记一本热力学账

**Where the Tokens Go: Heat, Entropy and Error in Agentic Coding** · Alán Aspuru-Guzik、Varinia Bernales（arXiv:2611.23375，cs.AI / cond-mat.stat-mech / cs.SE，2026-11-17）

**链接**：[arXiv:2611.23375](https://arxiv.org/abs/2611.23375)｜DOI [10.48550/arXiv.2611.23375](https://doi.org/10.48550/arXiv.2611.23375)

**摘要**：编码 agent 按 token 计费，而软件工程学对「一个 token 究竟买到了什么」从未给出说法。作者提出一套**软件热力学**：把 agent 生成的 token 计为成本，再把这个成本拆成**功（work）**与**热（heat）**；测试套件充当「软件版的麦克斯韦妖」，对每一次编码变更作出裁决。实验设计借自单分子拉伸—回折的经典实验：让 agent 反复对仓库做一处修改（coding）再把修改撤回（uncoding），每次方向都从一棵存好的参照树出发，逐次统计每次模型调用的 token，并要求回到起点。反复循环的成本离散度定义了「软件温度」，且该温度随模型采样温度上升。

核心发现：

- **在一次成功运行里，约 80% 的 token 产生于「没有让目标变更发生位移」的模型调用**，作者把这类 token 称为热。
- 一次变更的**自由能**（类比 Jarzynski 等式估计）只占一次成功运行平均成本的 **14%–22%**。
- **coding 的成本是 uncoding 的 1.1–1.5 倍。**

作者也承认那个「妖」并不完美：测试套件的裁决会随环境而变，而一个接受了坏变更的测试套件是有 token 代价的。

**为什么与「开源之道」相关**：这篇给开源社区提供了一个此前只能靠体感争论的东西——**把「维护负担」从形容词变成了一笔可分项的成本账**。过去说「AI 带来的噪音很累」，是感受；现在可以说：在 agent 自己的账本里，八成支出并不推进目标。这一条与本周 OpenSSF/LF 语境里反复出现的「AI slop 洪水」叙事是同构的，但它给的是**结构性原因而非道德原因**：噪音不是 agent 不努力，而是搜索过程的熵。

**「开源之道」点评**：我最想留下的是「妖不完美」那一段。测试套件是这套账本里唯一做判断的部件，而它被判为**会随环境变化、且会纵容坏变更**——这恰好就是开源里维护者与 CI 的真实关系：**CI 从来不是裁判，它只是把「被谁判过」这句话写进了 commit。** 一篇论文用物理学语言独立地走到同一个结论，说明这是结构性问题，不是某个项目没配好流水线。

三点必须说清。第一，这是**类比，不是推导**：热、功、熵、Jarzynski 在论文里都是从经典热力学借过来的形式映射，作者自己的措辞是 "by analogy"。**把它当作已经证明了的物理定律来引用，就是范畴错误**——这是本文最容易被误读的地方。第二，实验对象是「同一处修改的反复编码/撤回」，这是一个高度受控的合成任务；真实开源协作里没有「撤回到参照树」这种操作，**因此 80% 这个数字不能外推成「PR 里八成工作白做」**。第三，它的真正用途是**诊断而不是绩效**：如果这套记账能被工程化，项目就能分辨「改动没推动但调用很多」与「改动在推进但反复回退」，这对判断一个 agent 是在摸索还是在原地打转有用——但一旦它被拿去做贡献者的效率排名，就立刻变成了另一套「贡献定义权」。

#### 3. 能给 26 个同事发问，却只拿到 64% 的需求：agent 的困难不在写代码

**SWE-CoWork: Benchmarking Coding Agents as Digital Employees in Organizations** · Xinping Lei、Minghao Liu、Ruijie Zhu 等 26 人（arXiv:2611.20218，cs.SE / cs.AI，2026-11-15）

**链接**：[arXiv:2611.20218](https://arxiv.org/abs/2611.20218)｜DOI [10.48550/arXiv.2611.20218](https://doi.org/10.48550/arXiv.2611.20218)

**摘要**：一个在软件组织里工作的编码 agent，必须自己确立要建什么、与同事协作、并验证它交付的东西。作者构建了 **SWE-CoWork**：**101 个开发任务、101 个真实仓库、11 种编程语言、12 个应用领域**；每个任务把 agent 放进一个模拟工程组织，里面**有 26 位职责不同、知识有边界、协作行为受控的同事**。agent 从一份简短的交接说明起步，必须**把散落在同事与工作记录中的需求找回来、调和互相矛盾的证据、再实现变更**，并由私有可执行测试评分。

评测 11 个模型，核心发现：

- **两个最强的模型满足了约 63% 的 fail-to-pass 测试，却完成不到 8% 的任务。**
- 把完整需求事先交给 agent，可让 F2P 提升约 16 个百分点，但**完整任务成功率不变**。
- 轨迹分析显示失败分布在交付全程：Claude-Opus-5.5 平均把 **93% 的首次提问**指向被问卡片的**负责人**，但**只拿到 64% 的同事持有需求**。
- 被推迟的问题无人追问，需求到手后实现仍不完整，**31% 被报为完成的需求无法通过测试**。

**为什么与「开源之道」相关**：这篇把「agent 能不能当贡献者」这个问题从代码质量层面挪到了**组织信息层面**，并且给了一个可持续追问的量表：不是「它写得对不对」，而是「它有没有能力把一个分散在多人记忆里的需求，完整地搬到一次可验证的交付里」。开源社区的 issue 线程、RFC、邮件列表，正是这种「需求分散在多人记忆里」的极端形态。

**「开源之道」点评**：93% 的提问找对了人、却只拿到 64% 的需求——这两个数字的落差是整篇论文的制度核心。**找对人是一次路由，拿到需求是一次承诺**；前者可以靠检索与推断完成，后者必须靠对方愿意进一步解释、愿意把自己的隐性知识外化成文字。这正是开源社区里新人最常撞上的那堵墙：不是找不到维护者，是**找到了也没有人被义务回答**。而「31% 报为完成的需求通不过测试」与 11-21 那期报道的「37.24% 的工作报告含不实主张」是同一件事的两个测量面，互相独立地印证了「任务成功与自我报告可信度是两个属性」。

但必须限定。第一，**模拟组织不是真实组织**：26 位同事的知识边界与协作行为都是被设计的，agent 的「社交困难」是被测试环境构造出来的，不能直接读成「真实公司里的 agent 也这样」。第二，**8% 这个数字的使用要极小心**：得分条件是「完整任务交付」，而它的判据是私有测试——一个在开放协作里会被反复讨论、逐步澄清的任务，在基准里必须一次做对。这是基准的必然，但也意味着**它测的是「一次成型能力」，不是「协作能力」**。第三，这篇最有价值的产出其实是那句被推迟的问题无人追问——**这是可以被工程化的：任何 agent 的交付都应该带着「我还没确认的问题清单」**，而不是带着一句 Done。

### 📰 开源动态摘要

#### 1. 八年的产权重组收尾了，而收尾的方式比结果更值得记

**来源**：LLVM Discourse《Wrapping Up LLVM's Relicensing Effort》（@kbeyls，2026-11-19）｜媒体转述：Linuxiac《LLVM Wraps Up Eight-Year Transition to Apache 2.0 Licensing》（2026-11-21）

**摘要**：LLVM 宣布为期八年的重许可工作基本完成：**超过 99.5% 的历史代码行**现已纳入 `Apache-2.0 WITH LLVM-exception`，或已从代码库移除，或小到不构成版权保护。起点是 2018 年——当时项目要从 UIUC/NCSA 许可证（外加部分运行时库的 MIT）转向统一框架；2019-01-19 起所有**新贡献**都按新许可接收，而**改存量代码的许可条件必须拿到每一位原始版权人的许可**，这才是难的部分：八年间有 **1,300+ 名个人贡献者与约 100 家公司与机构签署协议**。官方同时明确写下**终止判据**：不再无限期追讨剩余的小部分；剩余的处理方式是给未签约者一条通道，让他们可以要求自己的早期代码带上对应的 SPDX 标识。LICENSE 文件与文档的更新将在 **LLVM 24 发布分支**（预计 2027 年 1 月初）之后落到 trunk，随 **LLVM 25** 发布。

**开源之道点评**：媒体的标题都在讲「用了八年」，但这条新闻真正的制度含量在**它怎么宣布结束**。任何一次全量产权重组都会遇到同一个问题：剩下那 0.5% 永远追不完，因为要找的人可能已经不用 GitHub、可能已经离职、可能已经去世。**没有终止条件的改革，最终会被自己的尾部长成新的僵局。** LLVM 的做法是给这次重组写上一句「够了」——并把残余风险的处置从「继续追」改为「登记 SPDX 标识、当事人自己来要求」。

这是奥斯特罗姆意义上的**边界规则**的一次清晰示范：公地治理不只是规定谁能进来、谁承担什么，还必须规定**什么时候停止执法**。一个永远在追欠账的社区和一个永不追欠账的社区一样不可持续；能写出「追到 99.5% 就收手，且剩余部分有损可查」的社区，才是把规则写完整的社区。

要克制一点：**99.5% 的分母是「历史上的全部贡献行」，不是「你今天 git clone 下来的代码」**——后者自 2019 年起就已经是 Apache-2.0 了。把这条消息读成「LLVM 刚刚换许可证」是彻底的误读，Linuxiac 特意点出这一点，值得记一笔：在开源新闻里，**最容易出错的地方永远是分母**。

#### 2. 一个密码学基础设施给自己建了「进入规则制定层」的入口

**来源**：OpenSSL Foundation《OpenSSL Foundation Joins the Open Source Initiative as an Affiliate Member》（Sherry S. Handel，2026-11-20；文中注明 OSI 于 11-13 正式确认）

**摘要**：OpenSSL 基金会宣布成为 OSI 的 **Affiliate Member**（准会员）。背景值得先记：OpenSSL 基金会成立于 **2014 年 Heartbleed 之后**，2024 年**以独立实体重新启动、配备自有员工**。成为 Affiliate 的收获被写成四条：在**政策快速变化时期**于 OSI 的治理与政策讨论中有发言权；与面对相同治理、许可、可持续性问题的同行基金会/项目建立更紧密关系；有更强的公共平台为关键开源基础设施的健康发声；以及为维持 OpenSSL 库的社区带来更多可见度。

形式上，每个 Affiliate 派出**一名代表**，而这位代表（本文作者）**同时承担三职：Affiliate 席位在 OSI 董事会的提名与投票、公共政策代表、媒体与传播代表**。文中还提到 OSI 于今年 9 月邀请其参加在加拿大哈利法克斯举行的 Open Source Congress。

**开源之道点评**：这条新闻小到几乎不会有人转发，但它是**一条完整的制度升级路径**：项目出事故（Heartbleed）→ 2014 年建基金会 → 2024 年独立化、雇人 → 2026 年进入标准组织的准会员席位 → 拿到董事会投票权与政策代表权。**十年，四步，每一步都没有戏剧性。**

#### 3. Google 把 agent 的执行层交给 CNCF：一次「托管即产品」的选择

**来源**：InfoQ《Google Donates Agent Substrate and gVisor to the CNCF to Secure AI Agents at Scale》（Craig Risi，2026-11-20）｜一手件：Google Open Source Blog《Sandboxing untrusted AI agents at scale》

**摘要**：Google 宣布把 **Agent Substrate** 与 **gVisor** 捐给 CNCF，另含开源强化学习编排项目 **OpenRL**，目的是让 AI agent 基础设施进入厂商中立的开源治理。

技术动机被讲得很具体：传统应用启动—服务—常驻，而 agent 常常只执行几秒工具或代码，然后等模型推理、等外部 API、等人工批准；Google 估计 **agent 有 90%–95% 的时间是空闲的，却仍持有重要状态**（内存、文件、仓库、活跃会话）。每个 agent 一个 Pod 太浪费，缩容到零再重建又太慢，大规模评测时成千上万个短命执行环境会压垮控制面。Agent Substrate 的做法是把 **agent 状态（actor）与执行它的算力（worker）分离**：actor 保状态，worker 是共享池里预热的执行环境；agent 恢复时分配 worker 并还原状态，空闲时保存状态、释放算力——**恢复时间可低于 500 毫秒，且不需要为每次执行新建 Pod**。安全侧由 **gVisor** 在用户态内核拦截系统调用，另支持 **Cloud Hypervisor microVM** 供需要硬件级隔离的负载选择。

**开源之道点评**：这条新闻的表面是「又一个捐赠」，制度上的实质是**托管权的分层**。Google 保留的是模型与 Agent 平台（产品），交出去的是**沙箱与生命周期管理**（执行层）。这与 Kubernetes 当年被交给 CNCF 是同一个动作：**把「所有人都必须依赖、且一旦被单方改动就会引发集体风险」的那一层，从公司资产变成公共基础设施**。

判断这一层是否真的被让渡，看的不是新闻稿的用词，而是三件可复核的事：TOC 与 TAG 的准入评级、maintainer 名册里 Google 之外的名字何时出现、以及 gVisor 在 K8s 之外是否真的被当成默认沙箱集成。

也要说清它没解决的问题。**捐赠执行层不改变模型层的控制权**，agent 的「大脑」仍然在少数公司手里；这跟 10 月那一轮「开放权重 ≠ 自主」的辩论是同一件事的两半——**开放的是跑道，跑道上的车还是自家的**。另外，「agent 90–95% 时间空闲」这个数字是 Google 的自报估计，用于论证其架构设计的合理性，**在拿到独立测量之前，它是产品论据而不是行业事实**。

### 🔍 Project Pulse：`django/django` —— 当「需求」本身不再留下痕迹

**项目**：[github.com/django/django](https://github.com/django/django)（Django Software Foundation；**91,884 ★ / 35,118 fork / 2,285 watchers / BSD-3-Clause / 最后推送 2026-11-21**，2026-11-22 实测）

**【L1 · 发布节奏】** 无新 release，最新 tag 停在 `stable/5.1.x` 系列；但主干推送未断（2026-11-21 16:52Z）。分支结构与 tag 命名（`stable/5.x.x` 长期并存）说明它仍在为**多个受支持版本**回移植补丁——这是「已有大量存量用户」的项目才会背的成本。**本月语义不是「上线新功能」，而是「维护多条支援线」。**

**【L2 · 治理结构 —— 本周的实测数据】** 治理宪章 `docs/internals/organization.txt`（11-17 已入库监测池 #64）把「合并权」写成明文章节：

- **Mergers 由指导委员会（steering council）挑选，人数维持在不少于 3 人**（理由是不让任何单人过载、防止单点燃尽）；**没有上限**。
- **禁止自合自审**：Merger 不得合并自己主笔的变更，除非得到另一位 Merger / 指导委员会成员 / triage & review 团队 / 安全团队成员之一的批准。
- **Merger 与指导委员会席位互斥**：当选即失去合并权。
- **DSF 可以用 Fellow 资金让这个角色可持续**——即规则允许「位置」与「钱」解耦，也允许用钱给位置续命。
- 合并权是**可撤销的**：被 CoC 委员会认定违规、或经指导委员会投票，均可解除。

**结构性对照**：11-21 那期深看的 mosquitto 是「一名贡献者 4,376 次提交、第二名 40 次」；Django 的制度回答是**先规定「不得少于三人」再谈其他**。

**【L3 · 社区活力 —— 一个不能说满的观察】** 最近 100 次提交由 **48 个不同账号**完成，第一名 `jacobtylerwalls` 17 次、第二名 `nessita` 11 次、第三名 `medmunds` 10 次——**集中度远低于单体维护型项目**。**PR 侧出现了值得记录的结构性事实**：按创建时间倒序的最近 100 个 PR 里，**处于已合并状态的只有 6 个**，其余绝大多数仍 open；而更早一个窗口（2026-10-01..11-21 已合并）约有 **40 个**——两边的口径与窗口不同，不能相减得出「积压翻倍」，但方向是清楚的：**提交侧的进水量远大于合并侧的出水量**。同时必须诚实记录一处**无法核对**：本项目 2026 年度的 issue 抽屉已迁出本仓库，`is:issue is:open` 返回 0，**「good first issue 板是否还活着」无法在仓库侧证实**——这本身就是一个治理可观察性的缺口，不是「新人入口已死」的证据。

**📌 开源之道判断**

把三件事排在一起看：**Mergers ≥ 3 的硬规则**、**100 次提交 / 48 个账号的分散度**、**访谈里的 FOSS Fridays**。它们指向同一个制度选择：**这个项目把「稀缺资源」明确认定为评审与合并，而不是代码。** 代码早就过剩了——现在连初学者都能一次生成十个 PR；真正稀缺的是「有人愿意读完、判断、并为之负责」。Django 的做法是把这份稀缺**制度化**：不让任何一个人独揽，不让他审自己的，让他一旦进委员会就必须交出合并权，并允许基金会用钱给他续命。

用威廉姆森的层叠说一句：这是 **L4（资源配置）的剧烈变化逼着 L3（治理机制）重新写规则**的现场。当贡献的边际成本塌向零，L4 上「提交」这个动作已经不是信号了；于是 L3 必须换一个信号——**能通过评审并承担责任的人才算贡献者**。这与 11-21 那期 mosquitto 的对照极为干脆：**单点项目靠伞形组织的「撤权通道」兜底，多点项目靠「不许单人掌权 + 禁止自审 + 三席下限」兜底**；两条路都在回答同一个问题——问责落在哪个「谁」身上。

一个必须提的隐忧。如果「写代码」变成不值钱的技能，而「评审」成了新人唯一的学习路径，那么**学习的入口就从「做一件小事」变成了「读懂别人做的大事」**——这对新人的认知门槛是升高的，不是降低的。Maron 用 Discord 上的定期活动去补这个落差，是聪明的做法（**社群补位制度**），但它依赖一个人的热情；**热情不是制度**。下一个该问的问题是：Django 的 triage & review 团队有没有**成文的加入路径与人数下限**？如果也没有，那这条新入口的可靠性与旧入口的 bus factor 一样脆弱。
