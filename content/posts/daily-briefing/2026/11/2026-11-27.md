## 「开源之道」 2026-11-27 搜集事件和材料

> 今天的线索落在同一个位置：**门槛**——当「门槛」以法律、认证或商业条款的形式出现时，开源如何被从外部重新定价。
>
> ① **LLM service freeloading**：513 个仓库、1,588 条推理路径，93% 建于 2026 年。在 62 家能查到条款的服务中，**58 家明文禁止了至少一种被观察到的做法**。这件事不构成法律上的模糊地带，它构成的是**共识上的模糊地带**——开源运动花四十年建立的「开放不等于免费取用」，在 LLM 这一层几乎完全失效，因为用户看到的界面就叫「免费」。
>
> ② **欧盟 MDR 与院内开源软件**：给「自己使用」留的缝，碰到一个致命细节——开源发布可能被判定为「投放市场」，而这是 MDR 明令禁止的。解法是把代码库切成两半：接口做公地，实现留站点。**共享只发生在最容易共享的那一层。**
>
> ③ **AI agent 的上下文文件**：41,090 条路径声明、184 条依赖规则。有执行的规则会被修好，没人检查的那 18% 从写入当天就错，而且几乎一直错下去。同一份文件里两类规则的可信度差一个数量级——**区别不在写法，在有没有一个强制执行的机制**。
>
> ④ **NVIDIA 把 OpenShell 捐给 CNCF Sandbox**：治理文档开出的药方，正好命中它自己当下的诊断。14 个 maintainer 席位里 11 席来自同一家公司——**捐赠 ≠ 转移**。

### 📄 最新开源研究论文

#### 1. 把「免费额度」当成新公地：LLM service freeloading 的系统测量

**论文**：Demystifying Real-world LLM Service Freeloading
**作者**：Xinyi Hou、Shenao Wang、Wenhui Pan、Yanjie Zhao、Haoyu Wang（华中科技大学等）
**链接**：[arXiv:2611.33218](https://arxiv.org/abs/2611.33218)｜DOI [10.48550/arXiv.2611.33218](https://doi.org/10.48550/arXiv.2611.33218)｜2026-11-24

**摘要**：第三方项目把大模型网页应用与专用客户端里的「免费推理」重新打包成独立 API 出售。作者把这套越出服务方允许范围（访问、配额、再分发条件）的用法命名为 **LLM service freeloading（LSF）**，并对 513 个开源项目、64 个上游 LLM 服务、1,588 条推理路径做了系统测量。

三个发现：① **93.0% 的仓库创建于 2026 年**——这是一个一年之内凭空长出来的生态；② 83.2% 的路径走直接 HTTP/WebSocket 请求，主要手段是**复刻产品协议**，而不是调用官方 API；③ 304 条路径（19.1%）出现账号选择或轮换，把请求分摊到多个账号各自的免费额度上。政策层面：在 62 家能查到条款的服务中，**58 家明文禁止了至少一种被观察到的做法**（自动化访问、账号共享、服务转售），禁令同时覆盖下游提供 API 与上游获取推理这两端。

**为什么与「开源之道」相关**：这篇文章把「搭便车」（free riding）这个奥斯特罗姆框架里最古老的问题，换到了一个全新的稀缺资源上：**不是代码，是推理配额**。代码是公地，配额是俱乐部品——这是一次典型的范畴错位。

开发者用「开源」这个词为「转售别人的免费额度」提供道德掩护，而真正的公地（模型权重、协议实现）和真正的私物（账号、额度）在同一个仓库里被混装。更值得注意的是那 19.1% 的账号轮换：这已经不是在贡献，是在**规避分配规则**。奥斯特罗姆讲的公地存续第一原则是「边界清晰」，LSF 生态的第一动作就是把边界擦掉。

**「开源之道」点评**：测量结果里最锋利的一条不是 93% 的新建率，而是 **58/62**。也就是说，这件事不构成法律上的模糊地带，它构成的是**共识上的模糊地带**：条款写得清清楚楚，社区里却普遍觉得「免费的东西拿来用不算偷」。

开源运动花四十年建立的那套「开放不等于免费取用」的语汇，在 LLM 这一层几乎完全失效——因为用户看到的界面就叫「免费」。真正的问题从来不在这些仓库，而在提供方：**用免费额度换分发，代价是把「公地」和「赠品」这两个词混成同一个词。**

#### 2. 当「公开发布」本身构成违法：欧盟 MDR 与院内开源软件

**论文**：The AMPEL Platform: A Concept for Open-Source Collaboration in Developing In-House Medical Device Software under EU-Regulation
**作者**：Daniel Steinbach、Maria Schmidt、Alexander Twrdik、Clemens Malkawi、Toralf Kirsten、Martin Federbusch（莱比锡大学医学中心等）
**链接**：[arXiv:2611.30858](https://arxiv.org/abs/2611.30858)｜DOI [10.48550/arXiv.2611.30858](https://doi.org/10.48550/arXiv.2611.30858)｜2026-11-23

**摘要**：欧盟《医疗器械法规》（MDR）第 5(5) 条给医疗机构留了一条缝：可以为「自己使用」而院内制造医疗器械软件（in-house MDSW），要求放宽。但这条缝有个致命细节——**把院内软件开源发布，可能被判定为「投放市场」（placing on the market），而这是 MDR 明令禁止的**。

作者基于莱比锡大学医学中心开发院内临床决策支持系统（CDSS）的实际经验、专家讨论、文献综述与一份正式法律意见，提出一条监管路径：把代码库切成两半——共享的开源代码库本身**不构成医疗器械**，可以公开发布与协作；但每个站点必须自己编写「数据输入」模块，并各自独立满足 MDR 对院内 MDSW 的全部要求。作者自己也承认，这对开源项目来说极不典型：「这给每个站点的部署留下了相当大的工作量。」

**为什么与「开源之道」相关**：这是一个开源从未遇到过的约束形态——不是许可证不兼容，也不是专利，而是**「公开发布」这个动作本身可能构成违法**。

MDR 把「投放市场」作为监管触发点，而开源的定义就是可被任何人获取和使用；两个定义在同一个动作上迎头相撞。作者的解法是抬出奥斯特罗姆式的边界工作：把「公地」（共享代码库）与「合规单元」（各站点的医疗器械）切开，让公地合法存在。这是把**产权边界画在代码目录结构上**的一次罕见实践。

**「开源之道」点评**：注意这个切法的代价。公共部分被压到最小（只是不含医疗器械判定的骨架），重复的部分被推到每个站点（数据接入、验证、文档、风险管理）。制度上这叫**成本外部化到最弱的一方**：大医院有法务和合规团队，小医院只能回头去买商业产品。

所以「开源让所有人平等」在这里变成了「开源让所有人平等地各自扛一遍监管」。这不是开源设计的失败——是监管的语法里**根本没有「共同开发但不共同上市」这个格**。开源要往前走，得先教监管者造出这个句式。

#### 3. 边界在工程上就是一份 Protobuf schema

**论文**：The AMPEL Platform: An Open-Source Project for Developing Hospital-Wide Clinical Decision Support Systems under EU-Regulation
**作者**：Alexander Twrdik、Daniel Steinbach、Martin Federbusch、Clemens Malkawi、Maria Schmidt、Toralf Kirsten
**链接**：[arXiv:2611.30990](https://arxiv.org/abs/2611.30990)｜DOI [10.48550/arXiv.2611.30990](https://doi.org/10.48550/arXiv.2611.30990)｜2026-11-23

**摘要**：前一篇的技术实现篇。AMPEL 是一个满足 MDR 要求、用于构建 CDSS 的开源平台：事件驱动、分布式，以 Kafka 消息中间件为核心，随医疗数据产生而实时处理并横向扩展。

关键设计是**平台接口通过「平台特有事件」隐式描述**，事件用 Protocol Buffers 定义，因此平台与具体医院信息系统解耦，医疗算法可由各方用任意语言独立实现再挂上去；平台自带基础 UI 与告警，在可追溯、可解释的前提下向医护呈现结果。文中以莱比锡大学医学中心实际运行的 LAMPE 为案例，并列出当前局限与后续计划。

**为什么与「开源之道」相关**：边界在工程上从来不是抽象概念——这里它就是一份 Protobuf schema。用消息契约代替函数调用，等于把组织之间的边界写成了**协议**：你知道对面是什么格式，但不知道对面是谁、在哪家医院、由谁维护。

这是开源跨组织协作的经典手法（从邮件列表到 API），只不过这次跨的是受监管的机构边界，而且协议本身承担了法律责任的分界功能。

**「开源之道」点评**：两篇合起来读，能看到一个很诚实的自我限定：**接口做成公地，实现留在站点**。这个分工在技术上完全合理，在制度上却说明了「共享」只发生在最容易共享的那一层——schema 比合规便宜，比部署便宜，比承担责任更便宜。

开源很多时候就是在这个意义上成立的：**把共同的部分收窄到刚好不产生责任为止**。这不是批判，是描述；但值得记下来，因为每次有人问「为什么开源没带来更多协作」，答案常常就卡在这条线上。

#### 4. Agent 的地图配得上领土吗：41,090 条路径声明与 184 条依赖规则

**论文**：Does the Agent's Map Match the Territory? Architectural Claims in AI Agent Context Files and Their Fit with the Code
**作者**：Bachan Ghimire、Daniela Damian（维多利亚大学）
**链接**：[arXiv:2611.29916](https://arxiv.org/abs/2611.29916)｜DOI [10.48550/arXiv.2611.29916](https://doi.org/10.48550/arXiv.2611.29916)｜2026-11-23

**摘要**：AI 编码 agent 每次会话都没有记忆，开发者用 CLAUDE.md、AGENTS.md 这类上下文文件填补这个空白，而 agent 把这些文件当真理。作者检查了 3,346 个开源项目里 3,602 份上下文文件中的 **41,090 条路径声明**和 **184 条依赖规则**，逐条对代码与历史做核验。

结果：约 5% 的路径声明指向找不到的路径，但估计真实错误只有 2.2%，与 README 的 3.5% 相当；代码移动后，**61% 变成过时的声明被修好，且多数在同一个 commit 里**。依赖规则则完全不同：184 条里 **33 条（18%）在写下当天就已经是错的**（通常被更早的代码破坏），而且**几乎全部一直错下去**——因为没人跑检查。

作者的结论很克制：上下文文件是「好地图，但不可靠的规则书」，它们描述的常是团队**希望**的架构，不是**实际**的架构。另有一项探索性对比：agent 辅助的 commit 破坏规则的频率约为其他 commit 的 1.8 倍（0.29% vs 0.16%），但只有 14 次，作者明确说明这不构成显著证据。

**为什么与「开源之道」相关**：这是「**书面规则与实际行动的偏离**」的一次大规模量化，而这是理解任何制度的第一步。路径声明有人用（编辑器会标红、agent 会撞墙），所以错误会被修；依赖规则没人执行，所以 18% 的错误从出生那天起就注定长寿。

同一份文件里，两类规则的可信度差了将近一个数量级——**区别不在写法，在有没有一个强制执行的机制**。开源社区的 CODEOWNERS、CONTRIBUTING、CoC 也全都在这条谱上：有人查的那几条活着，没人查的那几条只是装饰。

**「开源之道」点评**：论文最值得抄下来的一句是「规则常常描述团队想要的架构，而不是它拥有的架构」。这句话可以直接送进任何一份 OSPO 政策文件——**绝大多数开源治理文档写的是愿望，不是约束**。

而这个差别只有一种办法能测出来：像作者那样，把每一条规则拿回去对代码。做不到这一步的治理，本质上是一种公告。附带一提，作者在方法上也诚实得罕见：全程用 LLM 辅助但每步人工复核，并专门讨论了这对挖掘类研究的机会与风险——这本身就是一个值得学的样本。

#### 1. NVIDIA 把 OpenShell 捐给 CNCF Sandbox：代码进去了，治理没进去

**来源**：NVIDIA 官方博客（2026-11-10，KubeCon NA）；仓库 `ai-openshell/openshell`
**链接**：[blogs.nvidia.com/open-source-openshell-infrastructure](https://blogs.nvidia.com/blog/open-source-openshell-infrastructure/)｜[github.com/ai-openshell/openshell](https://github.com/ai-openshell/openshell)｜[CNCF landscape](https://github.com/cncf/landscape)

**摘要**：NVIDIA 在 KubeCon 上宣布把 OpenShell（面向自主 AI agent 的安全与策略运行时，Apache-2.0，Rust 实现）捐给 CNCF Sandbox，并将其描述为「由把它构建进产品的各个组织共同治理」。同期还向 Google 主导的 Agent Substrate 项目做出贡献，并开源了 DSX AI Factory 的三块组件（NVIDIA Kubernetes Engine、Kubernetes Recipes、NVIDIA Snapshot）。博客里写「数百家组织在用，上线不到一年收到数万次贡献」。

仓库数据：2026-02-24 建立，21,965 星、2,156 fork、806 个 open issue，最近一周 91 次提交。

**「开源之道」点评**：今天真正值得看的是仓库里那三份文件。

- `MAINTAINERS.md` 14 人：**NVIDIA 11、Red Hat 3，其他为零**。
- `REVIEWERS.md` 覆盖 5 个 area、89 条区域任职记录、17 个不同的人：**NVIDIA 12、Red Hat 4、Gretel 1**。
- `GOVERNANCE.md` 写得非常规范——贡献者阶梯、lazy consensus、Emeritus 机制，甚至专门写了一条自我诊断：「当一个组织主导项目决策或 maintainer 席位时，说明需要组织均衡投票或选举产生的指导机构」。

于是出现了一个精确的矛盾：**治理文档开出的药方，正好命中它自己当下的诊断**。捐赠到 Sandbox 改变的是托管方，不是席位分配；CNCF landscape 里它已经是 `project: sandbox`。判断一个项目的治理是否真的转移，标准从来不是博客里的那句话，而是**下一位 maintainer 来自哪家公司**。这条线索值得按季度回访。

#### 2. Apple 把 9 年历史的开源笔记应用从欧洲所有 App Store 移除，开发者近三周未获任何回复

**来源**：GitHub Discussion — `glushchenko/fsnotes` #2056（2026-11-23，HN 632 points / 180 comments）
**链接**：[github.com/glushchenko/fsnotes/discussions/2056](https://github.com/glushchenko/fsnotes/discussions/2056)

**摘要**：FSNotes 作者、乌克兰独立开发者 Oleksandr Glushchenko 公开：他的开源笔记应用被苹果从**所有欧洲国家的 App Store** 下架，无清晰解释。起因是 10 月销售款未到账；他开了两个工单（11-05 Case 23353628、11-17 Case 23573022），自 11 月 5 日起**没有收到任何回复**。

他已按欧盟《数字服务法》（DSA）补齐 App Store Connect 合规信息，并提交乌克兰政府商业登记处的官方文件。他强调自己是合法注册、依法纳税的个体经营者，但没有人审他的材料。他最在意的不是恢复上架，而是排名、搜索可见性、九年积累的可发现性。HN 讨论里最高赞的几条都在谈同一件事：官方客服要么外包无权、要么是廉价 LLM，**「跑去找媒体」成了事实上唯一的申诉通道**。

**「开源之道」点评**：代码的产权（MIT）在这里毫无争议——源在、编译在、fork 在，谁都能继续。失去的是**分发通路**，而分发通路从来不是产权问题，是准入问题。许可证解决的是「别人能不能用、改、再分发」，它一个字都没承诺过「你能不能到达你的用户」。

更值得记的是事件形态：不是**拒绝**，是**沉默**。拒绝可以申诉，沉默无处上诉——这是汲取性制度最省力也最有效的一种形态：不夺走你的东西，只是让你的东西留在原地发霉。评论区那句「upvote 现在成了客服入口」说穿了整个结构的形状。

#### 3. GitHub 讨论给 maintainer「关闭 PR」的权力：一个平台在替社区设计边界

**来源**：GitHub Community Discussion #185387（HN 139 points）
**链接**：[github.com/orgs/community/discussions/185387](https://github.com/orgs/community/discussions/185387)

**摘要**：GitHub 正在讨论是否给 maintainer 一个**关闭某个仓库 PR 通道**的控制项。这条讨论的背景是这一年里反复出现的事件：AI agent 批量开 PR、被关后写博客羞辱维护者（matplotlib #31132，HN 953 points，2026-02）；Ars Technica 根据被操纵的信息写出引语并撤稿（HN 555 points）；Socket 披露 AI agent 试图社工维护者以合并恶意代码。

这些事件有一个共同点：**施压方式不是技术攻击，是公关**。

**「开源之道」点评**：注意这个提议的制度含义。它把「收不收贡献」从一个**默认开放的社会惯例**，变成一个**可配置的平台开关**。这是把治理权从社区的规范层上移到平台的配置层——短期看是给维护者减负，长期看是让「开放」变成一项需要主动维持的设置。

开源运动默认的那条规则（PR 通道永远开着，你可以不理但不能关）从来没有写在任何许可证里，它一直靠社会压力维持；当压力反向（被羞辱的代价超过不理的代价）时，这条规则就撑不住了。**没有一个组织站出来定义「什么样的贡献算贡献」——于是平台用 UI 来定义。**

### 🔍 Project Pulse：`ai-openshell/openshell` —— 一份会自己诊断出自己病症的治理文档

**观察窗口**：2026-02-24（建仓）→ 2026-11-26

- **L3 治理机制层**（合同与组织安排）：OpenShell 的捐赠、GitHub 的 PR 通道开关、AMPEL 的「接口公地 + 实现留站点」。三者手法不同，共同点是把非正式安排转成可审计的规则——或反过来，把社会惯例降格为配置项。检验信号：OpenShell 下一位新 maintainer 来自哪家公司；GitHub 是否真的上线该开关，以及默认值是什么。

**误判风险**，三条：

① **LSF 的「93% 新建于 2026 年」不应被读成「开源社区在集体越界」。** 论文测的是仓库行为，不是人的动机；一批以「免费 API」为卖点的项目在这个窗口内集中出现，很可能与模型服务方分发策略的阶段性变化有关，而不是社区道德的突变。把责任归到开发者个体身上，正好错过了真正的杠杆点——提供方的免费额度设计。

② **OpenShell 的负面解读也可能是错的。** 一家公司主导一个新项目的席位，在项目成立九个月内是常态，未必是汲取性；治理文档写明组织均衡机制本身就是可用的纠偏路径。真正的判据不是今天的比例，而是**这个机制是否真的被触发过一次**。

③ **AMPEL 两篇是概念与实现的自述，不是监管裁决。** 作者自己承认「给每个站点留下相当大的工作量」，其法律意见来自单一机构。引用时应标注为「一种可行路径的论证」，不能当成 MDR 的既成解释。
