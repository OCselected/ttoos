## 「开源之道」 2026-11-16 搜集事件和材料

{{< figure src="/media/covers/daily-reading-2026-11-13.jpg" title="「开源之道」昨日阅读 · 2026-11-13" width="100%">}}

> 今天三条线索说的是同一件事的三个层次：**当 agent 既能写代码又能提交 PR，开源项目真正需要确认的不再是「代码写得好不好」，而是「谁做的事、谁签的字、谁在负责」。**
>
> ① **学术面出了一对孪生数据集。** **AgentTorrent** 在 GitHub **10,944 个「被工程化」的项目**里，记录了 **62,374 份配置制品**、**27,593 份 agent 规划文档**、**超过 120 万条标注了 AI 工具的提交**——它量出来的是一条制度性事实：**指令（AGENTS.md / CLAUDE.md / skills / hooks / MCP 配置）已经进入版本控制，成为仓库的一部分**。**GHAgentCI** 从 **196,000+ 个仓库**里取出 **6,000+ 个**、**15,000+ 份 workflow 历史**、**159,000+ 次修订**，三条发现里最像制度信号的是第三条：**检测到的 agentic workflow 被移除的频率很高**。
>
> ② **新闻面是一个最激烈的立场与一个最沉默的事实。** HN **713 分 / 385 条评论**的《All AI-generated code should be Open Source》主张：训练语料来自公地，产出凭什么可以私有——作者用的词是 **license laundering（许可证洗白）**。与之并列的是美国国税局 Direct File 仓库：**4,731 颗星、1,385 个 fork，总共只有 3 次提交、2 个署名**，README 自陈「已归档、不再维护、可能含未修补漏洞」。
>
> ③ **Project Pulse 抓到一个把三件事同时摆上桌的项目。** AgentRun 最近 100 个提交里 **91 个来自同一个 bot**，抽查 12 个已合并 PR 有 **10 个由提交者自己合并**——但 ruleset 里 **required_approving_review_count: 1** 是 active 的，且**确实被执行了**：批准人只有两位真人（`miguelrios` 10 次、`ajasver` 2 次）。**制度没有失效：门在，只是推门的人一直只有两位。**
>
> 一句话概括今天：**约束正在从「评审时对人说」前移到「提交时对 agent 写」，而共识仍在追问「签字的人是谁」。**

### 📄 论文两条

#### 1. 10,944 个仓库里的 62,374 份「写给 agent 看的文件」：提示词时代已经结束，被治理的是成本

**AgentTorrent: A Dataset of Context and Harness Engineering Artifacts on GitHub** · Sebastian Baltes、Seyedmoein Mohsenimofidi、Levi Böhme、Vahram Nersesyan、Muhammad Auwal Abubakar、Jai Lal Lulla、Matthias Galster、Christoph Treude（arXiv:2611.15436，cs.SE，2026-11-11）

**链接**：[arXiv:2611.15436](https://arxiv.org/abs/2611.15436)｜DOI [10.48550/arXiv.2611.15436](https://doi.org/10.48550/arXiv.2611.15436)

**摘要**：过去几个月，开发者的工作方式从「写详细的提示词」转向「设计 agent 读取的上下文、配置它底下的 harness」。具体表现是：开发者开始把上下文文件、skills、hooks、MCP 配置提交进仓库，这些文件决定 harness 读哪些指令、能采取哪些动作；同时也会提交 agent 或 spec-driven 框架写下的 spec、plan、task 文件。AgentTorrent 数据集在 GitHub 的 **10,944 个「被工程化」的软件项目**里，记录了六种（专有与开源各半）agentic 编码工具的这类文件：**62,374 份配置制品**、这些制品 import 的文件、**27,593 份 agent 规划文档**，以及**超过 120 万条标注了 AI 工具的提交**。所有采集启发式都锚定在工具官方文档上，并逐次评估检测准确率；项目是否「被工程化」用开放权重模型判定。与多数数据集不同，它把配置制品、被 import 的文件、规划文档、AI 署名提交**在同一仓库内串联起来**——三类同时出现的仓库有 **388 个**。据此可以研究：某个工具是否被记在自己那份指令的提交里、不同指令文件之间如何相互 import 又如何相互矛盾。采集管线支持定期更新，自动比对厂商文档、上报未知制品与未知工具；数据集与管线开源并归档在 Zenodo。

**为什么与「开源之道」相关**：这份数据集量出来的是一条**制度性事实**，不是技术事实：**指令已经进入版本控制，成为仓库的一部分**。这一点比任何「AI 政策」都重要——政策是文本里的意愿，指令是每次 agent 运行时**实际执行的规则**。当规则以文件形式进了 git，它就获得了三样东西：可 review、可 diff、可追责。11-11 简报里 Kafka 的 `AGENTS.md` 与 `CONTRIBUTING.md` 的「AI-Generated Contributions」小节在同一次合并里成型，是单点样本；这份数据集说明那**不是孤例，而是上万项目正在做的事**。

它也顺手给出了一个**可执行的反向审计入口**：388 个仓库里三类制品（配置、规划、AI 署名提交）同时出现——这 388 个仓库就是「谁在真正按 agent-first 工作、而不是偶尔问一下聊天框」的可复核名单。**「不删除、不覆盖、只追加」这条朴素纪律，在这里第一次有了机器可读的载体。**

**「开源之道」点评**：把它和 11-15 那篇 AI slop PR 的实证连起来读，会看到一条被反复忽略的因果：slop 论文说维护者靠直觉否决且不解释，本篇说开发者正在把「给 agent 的约束」写进仓库。**这两件事不是矛盾的，是同一次成本转移的两端**——产出端的成本塌陷之后，约束就从「评审时对人说」前移到了「提交时对 agent 写」。用威廉姆森的四层看，这是**从 L3（治理机制：评审、准入）向 L4（运行配置）的一次下沉**：规则没变少，而是变早了。

要克制的地方也在这里：数据集量的是**制品的数量**，不是**约束的有效性**。62,374 份配置里有多少条真的被执行、有多少条写完之后再没人看，这份数据集回答不了——就像 OSPO 的数量从来不能证明治理有效。**下一步的问题不是「有多少项目写了 AGENTS.md」，而是「写了却没人维护的那些，和没写的那些，产出质量有没有差别」。**

#### 2. 6,000 个仓库、15 万次流水线修订：当 agent 进了 CI，它的第一份工作是改别人的 CI

**GHAgentCI: A Dataset of Coding-Agent Invocations in CI Workflow Histories** · Daniel Ogenrwot、Jorge Gonzalo Delgado Cervantes、Woojoong Kim、John Businge（arXiv:2611.15522，cs.SE / cs.AI，2026-11-11）

**链接**：[arXiv:2611.15522](https://arxiv.org/abs/2611.15522)｜DOI [10.48550/arXiv.2611.15522](https://doi.org/10.48550/arXiv.2611.15522)

**摘要**：编码 agent 越来越多地被集成进 GitHub Actions 去评审 PR、分流 issue、修改代码，但**识别这些集成本身就很难**——agentic workflow 与普通 CI 文件长得很像，证据散落在 action 引用、shell 命令和 workflow 约定里。作者发布 GHAgentCI：从 **196,000+ 个挖掘仓库中的 6,000+ 个**里取 **15,000+ 份 workflow 历史**，含 **159,000+ 次修订**与 **205,000+ 条 agent 证据记录**，每条都关联到 workflow 触发器和声明的执行约束。开源抽取器 `cai-miner` 用可扩展目录检测 agent 证据；对 576 条分层样本做人工验证，专用 action 类匹配准确率 **96.1%**、GitHub Agentic Workflow 类 **98.8%**，其他证据类型准确率较低。探索性分析发现三点：①集成方式**正在从专用 action 转向命令行与 GitHub Agentic Workflow**；②不同集成方式**声明的防护措施（safeguards）差异明显**；③**检测到的 agentic workflow 被移除的频率很高**。

**为什么与「开源之道」相关**：三点发现里，第三点是最少被讨论、也最像制度信号的一条——**高频移除**。移除有两种读法，且需要证据才能分开：一种是实验失败（试了两周没用就撤），一种是**治理回撤**（发现权限过大、成本失控、或无法解释结果，于是拆掉）。CLI 与 Agentic Workflow 的兴起，与专用 action 的退潮，恰好指向第二种：**当 agent 通过官方 workflow 入口进来时，它继承的是平台的权限模型**——token 范围、secrets 可见性、fork PR 的隔离规则；而通过一个第三方 action 进来时，这些要自己守。于是同一种能力，两种入口意味着两套不同的风险敞口。

这一点对开源治理的直接含义是：**「agent 能不能改 CI」这个问题，正在被「agent 以什么身份改 CI」取代**。身份决定权限，权限决定出事之后谁承担。11-15 那篇 X 推荐算法的审计说「公开代码 ≠ 可被审计」，因为决定输出的环节不可达；这里说的是同一件事的另一种形态——**当 agent 的行为发生在流水线里，而不在提交里，出问题时的追溯链就断在 workflow 历史这一层**。

**「开源之道」点评**：这对数据集合起来，把「agent 治理」从宣言层拉到了可核查的层：**一篇数清了仓库里写给 agent 的规则（约束入口），一篇数清了流水线里被 agent 改过的动作（执行出口）**。两者都还没回答「效果」，但已经把「无从下手」变成了「有据可查」。

用奥斯特罗姆的话说，公地治理的第一条原则是**清晰界定的边界**。在 agent 时代，这条边界正在变成一个具体问题：**agent 以 bot 身份提交、以人类账号合并、以第三方 action 执行**——三个环节分属三种身份，边界就模糊在接缝处。谁把这三段缝起来，谁就定义了什么是「合法的贡献」。这也是本期 Project Pulse 要深看的东西：有一个项目，把这三段**全部交给 agent**，只留了一个人类按钮。

### 📰 开源动态摘要

#### 1. 一个 713 分、385 条评论的立场：AI 生成的代码全都该开源

**来源**：Jakub T. Jankiewicz 个人博客《All AI-generated code should be Open Source》（2026-11-15）｜Hacker News **713 分 / 385 条评论**（当日榜首）

**摘要**：作者的论证只有两条，但两条都很硬。

**第一条是训练数据的产权链**：AI 模型是在 RMS 宣布 GNU 工程以来所积累的**开源代码语料**上训练的，这些代码「直接被爬走，未经许可、未给署名」；训练语料里还包括以 **Creative Commons 许可发布、法律上要求署名**的 Stack Overflow 与 Stack Exchange 各姊妹站。把这份集体知识转成专有的闭源代码，作者用的词是 **license laundering（许可证洗白）**。

**第二条是版权适格性**：纯 AI 生成的代码**不是人写的，因此不应享有版权**。作者把法源追到著名的**猴子自拍案**——该案确立非人类不能持有版权，此后被美国版权局在 AI 相关决定中援引；同理，Wikimedia Commons 要求纯 AI 生成图像一律标注为公有领域。他也承认各国不同：**英国等司法辖区对「计算机生成作品」给予有限版权保护**。为跨辖区一致并回报成全了 AI 的开放生态，他主张开发者与公司**显式把 AI 生成代码以开源许可发布，或用 CC0 贡献给公有领域**。对于人机混合的部分，他划了一条主观但明确的标准：**代码不总是 100% 手工或 100% 自动，但当开发者已经「连看都不看」就采用生成结果时，这样的代码就该开源**。

**「开源之道」点评**：这条不该被读成「又一场 AI 立场之争」，它真正的价值是**在许可证层面提了一个可以被制度回答的问题**：当生成端的成本归零，「署名」和「出处」这两条最古老的非正式规范，靠什么执行？

注意它与 11-15 简报里 Asahi Linux 的决定是**同一现象的两个出口**：Asahi 面对「用 LLM 洗一遍以掩盖来源」，选择**收紧许可证**（MIT → GPL-2.0-or-later），把赌注押回可执行的正式制度；Jankiewicz 面对同一件事，选择**扩大开源义务**，把 AI 产出也纳入 copyleft 的射程。**一个在输入端设防，一个在输出端设防，两者都在承认同一个前提：洗稿的检测成本已经被击穿，只能靠许可条款重新把成本加回去。**

必须说清这个主张的三处脆弱。① **「AI 生成」的界线上不封顶**：文中自己也承认「部分自动」难以界定，而 Copilot 补全一行算不算，各家会给出完全不同的答案，任何以它为前提的强制开源都缺一个可操作判据。② **权属前提在多数辖区不成立**：美国讲「无人类作者即无版权」，但英国等辖区承认计算机生成作品的有限版权，**同一份代码在不同法域可能是「无主可开」vs「有主未开」**——这不是靠开发者自律能抹平的差异。③ **它默认了公地的供给是免费的**：如果 AI 产出必须开源，那么「用 AI 写闭源软件」这件事本身会被推向少数有能力自建模型的公司，**这条善意的规则可能反而加速集中**。

这个论证真正动人的地方不在结论，在于它问对了问题：**模型的训练语料是公地提供的，产出的许可归属凭什么可以私有？** 这句话在开源世界里已经问了四十年，只是这次被问的对象换成了模型。至于答案，把它交给许可证与法院，而不是交给立场，才是这个传统应有的做法。

#### 2. 一个已经死掉的政府开源仓库，被顶到 HN 首页：3 次提交、2 个作者、4,731 颗星

**来源**：GitHub `IRS-Public/direct-file`（HN 174 分 / 108 条评论，2026-11-14）｜许可证 CC0-1.0

**摘要**：美国国税局 Direct File——联邦个人所得税免费直报服务——的公开仓库，2026-11-14 被重新顶上 Hacker News。**抓取 GitHub API 的实际结果比评论区的讨论更说明问题**：

- **仓库规模**：4,731 ★ / 1,385 fork / 17 个 open issue，创建于 **2025-05-19**，最后一次 push **2026-06-11**（内容是更新 README）。
- **提交历史**：**总共 3 次提交**——`Initial commit`（2025-05-27）、`initial commit`（2025-05-29，均署名 `sps-irs`）、`Update README.md`（2026-06-11，署名 `SSP`）。**GitHub contributors 端点在默认口径下只返回 1 人。**
- **仓库自述**：README 明确写着「This repository has been archived and is no longer maintained. The code is provided for historical reference and may contain unpatched or unknown vulnerabilities. It should not be used in production systems.」（注：GitHub API 的 `archived` 字段仍为 `false`，即**自述已归档、元数据未归档**，两者不一致。）
- **许可证**：**CC0-1.0**——「As a work of the United States government, this project is in the public domain」，并额外在全球范围放弃版权。
- **被排除的部分（最要紧的一段）**：README 自陈并非全部源码与元数据都在仓库里。**凡涉及个人可识别信息（PII）、联邦税务信息（FTI）、敏感但非机密（SBU）、以及为国家安全的系统（NSS，40 U.S.C. § 11103）开发的代码，一律豁免**；「由于这些限制，若干功能已被移除或重写」。
- **法律依据清单**：SOURCE Act of 2024（Public Law 118-187，SHARE IT Act）、OMB M-16-21《联邦源代码政策》、FAR Part 27、FITARA、E-Government Act of 2002、Clinger-Cohen Act。
- **文档结构相当完整**：`docs/` 下分 `adr`、`design`、`engineering`、`product`、`rfc`、`testing`，ADR 从 2023-08 一直记到 2024-11（KMS 密钥管理、纳税人制品加密、生产分支策略等）。

**「开源之道」点评**：评论区争论的是「政府软件该不该开源」，但仓库本身给出的答案是另一个更锋利的题：**这是「开源」，还是「释出」？**

用 11-01 那道题的判据看（把「开放」拆成可检验的动作），这里是教科书级的**释出而非开源**：3 次提交、零外部贡献、没有维护承诺、自述「可能含未修补漏洞」——**没有协作通道，也没有人负责**。它满足开源的最弱定义（代码可见、许可极宽），同时几乎不满足任何一个强定义（可参与、可维护、可被社区接手）。**CC0 在这里是个反讽**：它把所有权利都放弃了，包括把「保证它还能用」的义务一并放弃。

但克制的话必须说：**这不是虚伪，而是政府软件的合法边界。** PII、FTI、NSS 的豁免来自成文法，不是部门的自选动作；SOURCE Act 要求的是「开源」，而美国法同时要求这些数据不得外流——两条法律对撞时，能做的只有**释出减配版**。真正的制度问题因此不是「为什么不给全」，而是：**当一个公共资金建设的系统只能以减配形式释出时，社区如何接手、接手了又由谁承担安全责任？** 这个仓库的答案是「没有人」，而这个答案才是它值得被记下来的原因。
