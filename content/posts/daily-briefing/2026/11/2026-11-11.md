## 「开源之道」 2026-11-11 搜集事件和材料

{{< figure src="/media/covers/daily-reading-2026-11-10.jpg" title="「开源之道」昨日阅读 · 2026-11-10" width="100%">}}

> 今天四条线索落在同一点上：**AI 生成物的洪峰撞上了公地的边界检测机制。**
>
> ① **先看人的那一侧。** 203 名使用编码 agent 的开发者里，仔细审阅了全部或大部分生成代码的人，**61% 仍然会在不细看的情况下批准至少一类 agent 动作**。最刺眼的是方向：**知道出过事故、了解可疑做法的人，反而更经常这样做**。这不是学习效应，是风险疲劳。
>
> ② **再看生态那一侧的可测绘性。** MCP 生态第一份独立于厂商的计数口径出来了：**78,302 个候选服务端，只有 5,138 个真的被用上**。发布成本几乎为零，采用成本才是筛选器。
>
> ③ **然后看钱与身份。** LF Research 年度报告：**72% 说 AI 是净正面，但 53% 的公司的外部贡献不足 10%**——社区是品牌资产，不是生产来源。同一周，LF Energy 拿到 250 万美元，钱不是投向研发，是投向**让小运营方也用得上**；ANS 用 DNS 给 agent 发身份证，把身份建在已有的分散信息上，而不是新建一个集中登记处。
>
> Project Pulse 今天给出一条以前没人画出来的曲线：**Kafka 的 300 个提交里 19.3% 带 AI 署名，而接住它的不是禁令，是一张 44 人的名册。**

### 📄 论文两条

#### 1. 开发者守住了代码评审，却把「动作审批」整片让了出去——而让得最多的人，恰恰是最懂风险的人

**From Delegation to Action Approval: An Exploratory Study of Developers' Practices in Collaborating with AI Coding Agents** · Yinan Wu、Dominik Wermke、Ze Shi Li、Kathryn Thomasset Stolee、Bowen Xu（arXiv:2611.10058，cs.SE，2026-11-06）

**链接**：[arXiv:2611.10058](https://arxiv.org/abs/2611.10058)｜DOI [10.48550/arXiv.2611.10058](https://doi.org/10.48550/arXiv.2611.10058)

**摘要**：开发者如今与编码 agent 协作——后者写代码，也**代开发者执行动作**。除审阅代码之外，开发者还要决定委托什么、批准哪些动作。有些动作（执行 shell 命令、读取文件）的效果**根本不会出现在最终代码里**。作者调查 **203 名**使用 AI 编码 agent 的开发者。三条发现：**其一**，细心的代码评审并不自动延伸到动作审批——**在那些仔细审阅了大部分或全部生成代码的人里，61% 仍然经常在未细看的情况下批准至少一类 agent 动作**；**其二**——这条最刺眼——**知晓安全或隐私事故、或了解可疑做法的开发者，反而更经常这样做**；**其三**，自治程度在开发者**个体之间**的差异，大于在开发活动类型之间的差异。多数人报告工作负荷变轻，但**监督本身仍然高度耗神**。被问到"什么会让你授予更多自治"时，超过一半的回答要求的不是更高的可靠性，而是 **agent 要"有界、可观察、可回退"（bounded, observable, reversible）**。

**为什么与「开源之道」相关**：这是今年第一份把"AI 协作"从**代码层**劈开到**动作层**的实证。代码层有公开的、可追溯的、有评审签名的制度（PR、review、CI）；动作层几乎什么都没有——一条 `rm -rf` 或一次外发请求，不留下 diff，不进入 CHANGELOG，不触发 CODEOWNERS。于是出现一个精确的制度错位：**公地积累了两百年的"审代码"程序，而 AI agent 的破坏力已经从代码里搬到了动作里**。更值得记的是第二条发现的方向性：**知情并不改进合规，反而降低它**。这不是学习效应，是**风险疲劳**——当一个人知道这条通道上确实出过事，而自己能做的只有一次次点"同意"，他的实际做法是加快点"同意"的速度。这正是奥斯特罗姆讲公地治理时最容易被跳过的一步：**规则的成本必须落在能改变结果的人身上，否则规则只是仪式**。

**「开源之道」点评**：把三条结论放在威廉姆森的四层里，故事很清楚：**L4（资源配置层的动作）已经全面 agent 化了，而 L3（治理机制层的审批）还停留在一个点击上**。开发者要的不是更强的模型，是**有界、可观察、可回退**——这三个词全是**制度词**，不是能力词。有界＝权限边界，可观察＝审计留痕，可回退＝可撤销权。这三条恰好是任何一套成熟产权制度的基础配置，而在今天的 agent 工具链里，它们是**可选项**，甚至不是可选项，而是**依赖厂商的心情**。对照昨日简报里那句"agent 不会维护制度，它只会遵守制度"：今天这篇补上了另一半——**人也不会维护制度，人只会维护自己还看得见的那一段**。代码看得见，所以评审还在；动作看不见，所以审批变得像点同意条款一样。开源世界真正要建的不是更好的 agent，是**给动作层补一套和代码层同等强度的制度**，而这件事没有任何一个厂商有激励单独去做。

#### 2. MCP 生态的第一张可测绘地图：78,302 个候选服务端，只有 5,138 个真的被用上了

**MCP-Eco: A Linked Dataset of MCP Servers, Consumers, and Development Activity** · Khalid Tounoussi、Mohammed Sayagh、Ali Ouni、Yutaro Kashiwa（arXiv:2611.06897，cs.SE，2026-11-04）

**链接**：[arXiv:2611.06897](https://arxiv.org/abs/2611.06897)｜DOI [10.48550/arXiv.2611.06897](https://doi.org/10.48550/arXiv.2611.06897)｜数据集 [MCP-Eco on Hugging Face](https://huggingface.co/datasets/mcp-research-alliance/mcp-ecosystem)

**摘要**：Model Context Protocol（MCP）让 LLM agent 能够访问外部工具与数据。要研究它的软件生态，必须把**服务端接口、配置了这些服务端的项目、以及它们的开发活动**连起来——但这些信息散落在目录站、包注册表、配置文件和仓库历史里。作者发布 **MCP-Eco**：一个把这些来源整合、并把"消费者配置声明"关联到"候选服务端项目"的关系型数据集。冻结版含 **16,880,899 条记录、19 张 Parquet 表**，覆盖 **78,302 个候选服务端项目**、**16,165 个候选消费方仓库**、**9,200 条配置声明**；其中**只有 5,975 条声明解析到了 5,138 个确定的"仓库—服务端"配对**。数据集还收录工具/资源/提示词的描述、声明的依赖，以及关联的开发记录（PR、评审、issue、提交）。**出处字段（provenance）明确区分**：目录站自报的能力、实时探测观察到的能力、以及文档发现来源与声明匹配方法——三者不可混用。

**为什么与「开源之道」相关**：MCP 从 2025 年底起已经是 Linux Foundation 旗下的旗舰项目，但**它到底是一个生态，还是一堆目录里的名字**，此前只能靠厂商新闻稿判断。这篇给出了第一个**独立于任何厂商的自陈**的计数口径。**78,302 → 5,138**，这个落差不是数据集缺陷，是**生态的真实形状**：发布成本几乎为零，采用成本才是筛选器。更值得学的是它的**方法论洁癖**——把"目录站说是这样""我实际探测到是这样""文档里写着是这样"分成三列并永不合并。**这是给整个开源供应链研究做的一次示范**：过去十年我们统计开源项目时最常见的错误，就是把"注册了"当成"存在"，把"声明了"当成"用了"。

**「开源之道」点评**：这个数据集的真正价值不在数字，在**它把"可测绘性"本身当成了一项基础设施来建**。开源之所以能被治理，前提是有人愿意付出成本去**独立核实**。而这恰恰是公地最缺的一件东西：**没有任何一个参与者有激励去核实别人的项目是否真的被用了**——你的竞争对手不会做，平台方做了也不会说真话。于是所有关于"生态有多大"的讨论，实际上都在引用同一批**没人核实过的自报数据**。MCP-Eco 是一小步，但它指向的命题很大：**AI agent 生态的治理权，最终会归给能为它建度量的人**。对照大分流 2.0 的框架——如果一个生态的度量标准由平台方自己定义并自己发布，"生态"就退化成了一份**行政统计**；而这份数据集之所以值得记下来，是因为它站在了相反的位置：**先声明口径，再发布数字，允许任何人复核**。

### 📰 开源动态三条

#### 1. LF Research 年度 COSS 报告：72% 说 AI 是净正面——但净正面全在内部，而 53% 的公司的外部贡献不足 10%

**来源**：[LF Research《The State of Commercial Open Source 2026》官方新闻稿 2026-11-10](https://www.linuxfoundation.org/press/new-linux-foundation-research-at-web-summit-72-of-commercial-open-source-companies-report-net-positive-ai-impact-brand-and-trust-not-code-ranks-as-top-comp-1793987251744)｜[PR Newswire 2026-11-10](https://www.prnewswire.com/news-releases/new-linux-foundation-research-at-web-summit-72-of-commercial-open-source-companies-report-net-positive-ai-impact-brand-and-trust-not-code-ranks-as-top-competitive-advantage-302933019.html)｜[报告全文 PDF](https://www.linuxfoundation.org/hubfs/Research%20Reports/LFResearch_COSSReport_102926.pdf?hsLang=en)

*（作者 Sam Boysel / Anni Lai / Matthieu Lavergne，Serena 合作，AWS、Red Hat、Futurewei、CNCF 赞助，**N=225**，误差 ±6%，数据经 Zenodo `linux-foundation-research` 社区开放。）*

**摘要**：报告在 Web Summit（里斯本，11-10）发布。核心数字：**72% 认为 AI 对公司是净正面（8% 负面）**，但收益来源高度集中在内部——**生产率/开发速度 73%**、新用例与更大 TAM 46%、新变现手段 39%；**43% 说 AI 完全没有改变他们的开源策略**，在做了调整的公司里，**开得更多（23%）几乎是关得更多（13%）的两倍**。AI 相关岗位是唯一净增长的岗位类别（38% 增 vs 6% 减），而非 AI 岗位与总人数均为持平至净减。竞争壁垒：**57% 说"品牌认知与信任"是第一优势**，远高于企业级功能、集成、社区规模（各 38%）；变现靠支持服务（63%）、托管云（49%）、open core（43%），**中位数跑两种模式、33% 跑三种以上**。open core 留出来的功能高度一致：**企业集成 63%、SLA 63%、高级分析 49%、审计/合规 48%；协作功能只有 27%，垫底**。而最关键的一条在社区那一节：**53% 的公司说外部贡献占其主开源项目的比例低于 10%**，只有 **11% 超过 50%**；**81%** 的公司说社区对路线图"至少有偶尔影响"，但"社区驱动路线图"的只有 **15%**。另有计量盲区：**38% 不测免费转付费转化率，42% 不测首次签约时长，25% 不测 CAC 回收周期**。

**「开源之道」点评**：这份报告最有价值的一句，是那句不起眼的"**协作功能是留得最少的（27%）——公司不对让工具扩散的机制收费**"。它无意中说清了 open core 的产权逻辑：**收费的边界不在"代码多少"，而在"价值在哪一层被组织放大"**。企业集成、SLA、审计合规——全是**跨组织规模才出现问题**的东西；协作功能——是**让更多人进来**的东西。于是 open core 不是"开一半关一半"，是**按组织规模的临界点切开**：进来免费，出去付钱。这与"开源是俱乐部品非公共品"的判断完全吻合，但更精确：**它在俱乐部内部又切了一刀，把"成员资格"和"成员规模的溢出效应"分开计价**。

但报告里真正需要停下来看的是 53% 与 11% 这两个数。**超过一半的商业开源公司，其主项目的外部贡献不足十分之一；能称得上"社区共治"的不到八分之一**。把这一条与 57% 的"品牌与信任是最大优势"并读，含义就出来了：**社区对这些公司是品牌资产，不是生产来源**。这不构成道德指控——报告自己也很坦白，而 2025 版已经用 800 家 VC 数据证明了 COSS 在估值与退出上的优势。问题在于这套模型现在被 AI 推到了新的位置：**AI 让内部生产率提升 73%（省下的是自己的活），却让外部贡献的甄别成本大幅上升**（昨日 LF 报告已测：60% 说 AI 助手增加了外部包，传递依赖只有一半被看；25% 的入站 PR 被认作 AI slop）。于是最自然的动作不是"多开门"，而是"**把门做成筛子**"——今天 Project Pulse 里 Kafka 与 vLLM 的实测，就是这道筛子的两种造法。社区仍然是护城河，但护城河里的水，正在被换成自己灌的。

#### 2. Google.org 出 250 万美元给欧洲电网的开源工具——钱买的是「小机构也能用」，这才是公共品该有的形状

**来源**：[Linux Foundation 新闻 2026-11-10（Enlit Europe，维也纳）](https://www.linuxfoundation.org/press/lf-energy-receives-2.5-million-in-funding-from-google.org-via-inco-to-advance-open-source-tools-for-europes-power-grids)｜[LF Energy 官方页](https://lfenergy.org/lf-energy-receives-2-5-million-in-funding-from-google-org-via-inco-to-advance-open-source-tools-for-europes-power-grids/)｜[Renewable Energy Magazine 2026-11-10](https://www.renewableenergymagazine.com/miscellaneous/lf-energy-receives-2-5-million-in-20261110)

**摘要**：LF Energy 与 Linux Foundation Europe 获得 **Google.org 经 INCO 拨付的 250 万美元**，两年期，投向四个已有的开源电网软件与数据项目：**OpenSynth**（不暴露客户信息的合成能源数据，供研究热泵、电动车、光伏的接入影响）、**PowSyBl**（已在法国 RTE 投产的潮流计算框架）、**Power Grid Model**（台区级高性能计算引擎，可一次跑数千个场景看哪里会过载）、**OpenSTEF**（短期负荷预测）。除开发外，资金还覆盖**培训、支持资源与采纳计划**，执行主任 Alex Thornton 的说法点明了方向：欧洲不可能靠新建线路追上需求，近期只能靠软件与数据榨出现有电网的容量；而**"因为工作是开源的，收益能到每一个运营方，而不只是那些自己有钱建这些能力的运营方"**，重点扶持**资源较少的小型与区域运营方**。Google 方面的表述是"不只是新物理基础设施，还需要开放的数字工具"。

**「开源之道」点评**：这条新闻值得记的不是金额（250 万美元在 AI 基础设施语境里很小），而是**它怎么被拆分使用**。四个项目里三个是**已经在生产环境跑着的**（RTE、TenneT、Alliander 一类大型运营方），钱的用途不是"研发"，是**让这些工具下沉到没有工程师储备的小运营方手里**——培训、支持、采纳计划各占一块。**这是一次罕见的、正确的公共品资助设计**：开源项目的产出本来就对所有人可得，真正的门槛从来不是许可，是**吸收能力**。你在 GitHub 上放一个比商业软件更好的潮流计算引擎，一个只有三名工程师的地区电网公司仍然用不上它——因为没有部署知识、出问题时没有人接电话。大多数"开源公共品"论证在这里断掉了，这份资助在这点上没有断。

反过来看，这也是它比不上"政府拨款"的地方：**钱来自一家公司，去向由一家基金会决定，而受资助的四个项目全部已经在同一家基金会的屋檐下**。这在威廉姆森的语言里是一个很干净的 L3 安排——交易成本低、协调顺畅、可执行——但它同时意味着**"谁的需求被写进路线图"这个问题，答案基本已被框定**。真正的检验点不在今天，在两年后：**这四个项目里，来自小型运营方的贡献者有没有从 0 变成非 0**。如果只有使用量上去、贡献者名单没变，那这 250 万买到的就是一次成功的分发，不是一次成功的能力建设。**这条判断标准现在就可以写下来，两年后回看。**

#### 3. Linux Foundation 接下 Agent Name Service：用 DNS 给 agent 发身份证——「身份不从网关来」，这句话的制度分量

**来源**：[Linux Foundation 新闻 / PR Newswire 2026-11-10（KubeCon NA，盐湖城）](https://www.prnewswire.com/news-releases/linux-foundation-welcomes-agent-name-service-to-bring-verifiable-identity-and-discovery-to-ai-agents-302935151.html)｜[ANS 官网](https://ansinfo.ai/)｜[规范与代码 github.com/agentnameservice](https://github.com/agentnameservice)｜缘起：[2026-06-23 启动意向公告](https://www.linuxfoundation.org/press/linux-foundation-announces-intent-to-launch-agent-name-service-to-establish-trusted-identity-infrastructure-for-ai-agents)

**摘要**：ANS 正式成为 Linux Foundation 项目。规范共**七份文档**：域锚定命名、注册与版本化、DNS 发布、公开日志审计、完整性监控、agent 间认证。技术路线是**把 DNS 与网站已在用的证书体系延伸到 agent**：组织用自己的域名标识自己的 agent，**没有专有命名空间、没有网关人**。已有 **11 家组织**参与贡献或采纳：Cisco、Cloudflare、DigiCert、DistributedApps.ai、GoDaddy、HOL、Infoblox、Radix、Salesforce、OWASP、Trustmodel.ai。互操作方面：AGNTCY 的 Agent Directory Service 支持校验 ANS 身份；ANS Finder 实现了 Agentic Resource Discovery（ARD）规范并通过其注册表一致性测试。规范由项目自己的技术指导委员会（TSC）在开源下继续演进，初始开发的主导者 Ken Huang（DistributedApps.ai）将加入 TSC。Cloudflare CTO Dane Knecht 的引述直指缘起：**近期多起高关注度的 AI agent 安全事故，证明了"在信任一个 agent 去行动之前，必须先知道它代表谁"**。
