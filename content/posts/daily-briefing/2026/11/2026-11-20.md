## 「开源之道」 2026-11-20 搜集事件和材料

> 今天三组材料围绕同一个问题打转：**当「产出成本」和「释出成本」同时被压到接近零，开源世界里用来区分「公地」和「单向发布」的那套信号，还剩下什么？**
>
> ① **学术面只有一篇与「开源 × 制度」直接相关，但它把问题问在了正确的位置上。** 三位作者以 OECD 公司治理原则、巴塞尔委员会指引、瑞士 FINMA 通函为基准，把 DAO 的议事、投票、问责三类机制逐项映射上去，得到一个结构性判断：**DAO 没有替代治理，它把治理保留下来并重新分配**——分给代币持有者、委托代表、社区论坛、智能合约、法律包装实体五种载体。代价是四个既有框架捕捉不到的风险：投票权集中、提案控制薄弱、法律不确定性、问责主体不清。这五个载体，与开源项目里的维护者、基金会理事会、TOC/TSC、CI 机器人、许可证，是同一张解剖图。
>
> ② **新闻面是两份性质完全不同的账本。** Google 主组织 2,947 个公开仓库，Apache-2.0 占 81.0%，2026 年新建 128 个仓库里 Apache-2.0 占 85.9%——**全年只开了 1 个 MIT、1 个 MPL、1 个 GPL-2.0 的新仓库**。与此同时，2026 年这 128 个仓库里，**68 个从来没有人开过 issue，39 个从来没有人 fork 过，91 个 ≤10 星**。许可证是统一的，公地不是。另一份账本来自 Lovable：AI 把「重写一个通用依赖的其中一层」的成本压低之后，`exit without voice`（退出而不发声）变成了一种比 fork 更划算的选择——**它用上游的许可证、上游冻结的架构，却不向上游输出任何东西**。
>
> ③ **Project Pulse 挑了一个小到几乎不值得写的仓库：`google/iso-c-chaining`，8 ★ / 1 fork / 0 open issue / 0 PR / 27 次提交 / 1 位贡献者。** 选它是因为它干净。Google Open Source Blog 为它写过一篇技术长文——**宣发级投入，换来 8 颗星**。这两个数字之间的距离，就是本周所有材料的共同结论：**宣发的规模与采纳的规模，在成本塌了之后完全不相关。**

#### 1. DAO 没有发明新治理，它把治理拆散后分给了五种人——一份 OECD/Basel/FINMA 对照下的风险测绘

**Governance Risks in Decentralized Autonomous Organizations (DAOs): Implications for Traditional Financial Institutions** · Christian Plöschberger、Irene Buller、Mark Christopher Ballandies（arXiv:2611.23201，cs.CY，2026-11-17）

**链接**：[arXiv:2611.23201](https://arxiv.org/abs/2611.23201)｜DOI [10.48550/arXiv.2611.23201](https://doi.org/10.48550/arXiv.2611.23201)

**摘要**：作者处理的是一个正在变成实务问题的题目：当受监管金融机构通过 DeFi、稳定币、代币化资产依赖「由 DAO 治理或部分治理」的系统时，传统风险管理框架还够不够用。方法不是田野调查，而是**规范对照**——以 OECD 公司治理原则、巴塞尔委员会指引、瑞士 FINMA 通函为基准，把 DAO 的议事（deliberation）、投票、问责三类机制逐项映射上去，再用若干真实案例做风险图示。

核心发现是一个结构性判断：**DAO 没有替代治理，它把治理功能保留下来并重新分配**——分给代币持有者、委托代表（delegates）、社区论坛、智能合约、法律包装实体（legal wrapper）五种载体。这样一来产生了四个既有框架捕捉不到的风险：**投票权集中**、**提案控制薄弱**、**法律不确定性**、**问责主体不清**；同时给出两个可迁移的优点：**可追溯的决策记录**、**批准与执行的直连**。论文最后给了一套结构化评估框架，主张把 DAO 治理特性接入机构现有的治理、外包、技术风险、运营韧性四类流程，而不另起一套风险框架。

**为什么与「开源之道」相关**：这是我读到的第一份把 DAO 治理风险写进**监管语言**而不是理想语言的材料。它的问题意识和开源治理研究高度同构——**当决策权被分散到多个载体，问责落在哪里？** 开源社区里同构的现象是：维护者、基金会理事会、TOC/TSC、CI 机器人、许可证，同样是五种载体；「投票权集中」对应大厂 committer 集中，「提案控制薄弱」对应 RFC 流程形同虚设，「问责主体不清」对应 bus factor=1 时的沉默。这篇论文的对照表虽然以 DAO 为对象，但**它给出的诊断项可以原样搬到基金会伞下项目的体检表里**。

**「开源之道」点评**：这篇的方法很保守（规范对照 + 案例插图），结论也因此可靠但不出新。真正值得抄下来的是它那句结构性发现：**去中心化不等于权力消失，等于权力换了载体且不再有单一问责点**。这正是奥斯特罗姆提醒过的事——公地的边界规则不会因为「没有中心」而消失，它会被写进某些默认值里；只不过在 DAO 里这些默认值是**智能合约代码 + 法律包装实体的注册地选择**，而在开源项目里是 **CODEOWNERS 文件 + 基金会章程**。两者都是「看起来中性、实际分配权力」的文书。

需要泼的冷水有两盆。第一，**对照基准是金融监管，不是民主治理**——OECD 原则和 Basel 指引是为上市公司和银行写的，把它们套到 DAO 上，结论必然是「DAO 在这些维度不合规」，这在方法上近乎自证。真正该问的是：**当一个系统明确不打算追求上市公司式问责，但它持有大量他人资产，问责的下限该由谁定？** 这个问题论文没有提。第二，**它把「透明可追溯的决策记录」列为 DAO 的可迁移优点，这一步走得太快**。链上记录的是**投票结果的不可篡改性**，不是**议事过程的可见性**——提案在 Discord 和论坛里怎么被磨掉的、谁在会前见了谁，链上一个字节都没有。开源社区其实提供了更好的反例：**邮件列表是真正可追溯的，而它恰恰正在被私聊和 Zoom 取代**。可追溯性不是技术属性，是**愿不愿意留下记录的制度选择**。

### 📰 开源动态摘要

#### 1. Google 的许可证账本：2947 个仓库，Apache-2.0 占 81%；2026 年新建 128 个仓库，Apache-2.0 占 85.9%

**来源**：GitHub API `orgs/google/repos`（2026-11-20 实测）｜背景：Google Open Source Blog 2026-11-18《Two decades of The Apache Way》（20 周年纪念文，页面当日已 404，标题与日期取自 Google News RSS，正文未能核实，故不引用其内容）

**摘要**：与其转述一篇纪念文的抒情，不如直接把账本调出来。实测数据：

- **全量 2,947 个公开仓库**：Apache-2.0 **2,386（81.0%）**、NOASSERTION 164、无许可证 156、BSD-3-Clause 130、MIT **49**、CC-BY-4.0 21、GPL-2.0 **17**、BSD-2-Clause 6、GPL-3.0 6、LGPL-3.0 2、EPL-1.0 2、MPL-2.0 2、PostgreSQL 1、CC0-1.0 1。
- **2026 年新建 128 个仓库**：Apache-2.0 **110（85.9%）**、NOASSERTION 8、无许可证 7、MPL-2.0 **1**、MIT **1**、GPL-2.0 **1**。**全年只开了 1 个 MIT、1 个 MPL、1 个 GPL-2.0 的新仓库。**
- **释出形态的另一半**：2026 年这 128 个仓库中，**0 fork 的 39 个**、**open issue 为 0 的 68 个**、**≤3 星 60 个**、**≤10 星 91 个**。
- **反例极少但不是没有**：`giflib-rs`（MIT，37★）、`abfs-casfs`（GPL-2.0，15★——是这一页里唯一一个 copyleft 的新建仓库）、`three-live`（462★ / 57 fork，是 2026 年新建里仅有的一个真有外部活动量的）。

**开源之道点评**：这组数字能说明的事，比任何纪念文都硬。

第一，**Apache-2.0 不是「选出来的」，是「默认值」**。81% 的全量占比、85.9% 的新建占比，意味着 Google 的开源部门不需要在每份新仓库前开一次会——制度已经把答案写成了模板。这正是诺斯所说的**非正式约束的成本优势**：当所有人都预期这件事该这么做，协调成本就是零。它的效率很高，代价是**这个组织在许可证维度上基本丧失了实验能力**。

第二，**许可证宽严与释出形态是两个独立变量**。91/128 的仓库 ≤10 星、68/128 的仓库零 issue——**绝大多数「Google 开源」的真实形态是「公开的单向释出」**，与 CC0 的 IRS Direct File（11-16/11-20 两次报道）在制度归类上处于同侧。**Apache-2.0 的宽并不能把释出变成公地**；能变成公地的，是有人提 issue、有人 fork、有人被合并。

第三，那条唯一的新建 copyleft 仓库 `abfs-casfs`（GPL-2.0，2026-09-30，15★）值得单独记一笔：在一个 81% 宽的账本里出现一个 GPL-2.0，说明**它不是被许可证政策选出来的，是被具体场景逼出来的**——通常是「上游本来就是 GPL，做内核/构建集成时无从绕开」。**大厂的许可证决定权，往往不在法务，在依赖树。**

需要克制的两点：**①「有 issue」不等于「可协作」**——Google 很多仓库开着 issue 但不接受外部 PR（贡献前需签 CLA、且多数仓库无 CONTRIBUTING 通道）；**②这次统计只覆盖 `google` 组织**，不含 `GoogleCloudPlatform`、`google-research`、`tensorflow` 等独立组织，所以它是「主组织画像」而非「Google 全貌」。但作为**同一个法人、同一批模板、跨越十年**的样本，它的稳定性本身就是一个制度事实。

#### 2. 一次由 AI 完成的「单方面私有分叉」样本：Lovable 用 Rust 重写 Vite 的开发服务器

**来源**：Socket.dev《Lovable's OJ Rewrites Vite's Dev Server in Rust as AI Lowers the Cost of Forking Open Source》（Sarah Gooding，2026-09-22）｜相关：`vite`（MIT）、Evan You（VoidZero）的公开发言

**摘要**：Lovable 把其云预览环境里的 Vite 换成了自研的 Rust 工具 **OJ**。动机极其具体：每天要起约 **100 万个短命开发沙盒**。生产灰度结果：**沙盒获得时间中位数 14.5 秒 → 3 秒**，dev server 进程内存占用降低约 **6.5 倍**。

技术边界要划清：这不是「重写 Vite」。OJ 与 Vite 共用 Rolldown 打包、Oxc 解析转换，两者都由 VoidZero 维护、也已在 Vite 8 中启用。**OJ 重写的只是 dev server 这一层**——把文件监听、模块图、编译器协同、热更新、WebSocket 处理搬进一个 Rust 二进制，并通过兼容桥跑 Vite/Rollup 风格插件，必要时起一个小 Node 进程。Evan You 在 X 上明确否认「整仓重写」。作者点出的关键趋势是：pnpm 12 的 Rust 重写是**原维护者带队**、Rspack 保留 webpack 配置与 API、Biome 高度兼容 Prettier——**而 OJ 是「按自己基础设施的需求，重写一个通用依赖的其中一层」**，且 Evan You 认为 AI 会让这类做法变得常见得多。

**开源之道点评**：这条新闻的价值不在「又一个 Rust 重写」，在它把**分叉（fork）的成本结构**摊开了。

传统 fork 之所以稀少，是因为它要一次性支付两笔钱：**重建维护能力**（自己扛 issue、安全响应、生态兼容）和**承担信任损失**（用户会问「为什么不用上游」）。OJ 走的第三条路——**不分叉、不回报、只替换掉自己最痛的那一层**——把这两笔钱都绕过去了。它用的仍是上游的许可证（MIT 允许），消耗的仍是上游冻结的架构（模块图、插件协议、配置格式），**但它不向上游输出任何东西**。用赫希曼的话说，这是**退出而不发声**（exit without voice）的极致形态。

真正的制度变量不是「AI 让重写变便宜」，而是**许可证给了这次退出合法性，而治理结构没有给它留下必须回来报告的义务**。MIT 在这里不是问题——问题在于开源世界里「分叉」这项权利长期与「维护」这项义务捆绑（你 fork 了，你自己扛），而 **AI 把义务那一半拆掉了，只留下权利那一半**。这正是 copyleft 存在的原始理由：copyleft 不阻止你改，它要求改完的东西**回到同一个许可空间**，从而强迫回馈。用威廉姆森的四层：**L4（生产行为）的成本已经被 AI 降到很低，而 L2（产权规则）还停在「你改你的、互不相干」的原状**——落差就在这里。

三处不能说满。第一，**OJ 针对的是极窄的目标**（Lovable 自己的预览沙盒），把它当作「Vite 将被取代」是误读；Vite 要覆盖的框架、插件、应用形态远比 OJ 宽。第二，文章给的收益数字（14.5s→3s、6.5x 内存）**是 Lovable 自报的受控 rollout**，不是第三方复现；换算到通用场景要打折。第三，也是最要紧的一处：`abfs-casfs`（新闻 1 里的那个新建 GPL-2.0 仓库）和 OJ 放在一起看，指向同一个方向——**AI 时代的许可证选择，会越来越取决于「我需不需要逼别人回来」，而不是「我相信什么」**。这两件事同时发生，才是值得记下的。

#### 3. 一年后回看「靠 AI 建出来的内部工具」：它不缺代码，缺的是没人写的那 90%

**来源**：bacon roll《Vibes Don't Maintain》（Alex，2026-10-14，HN 121 分 / 47 条评论）｜对照：HN 2026-11-18《Show HN: ExitPath》（245 分 / 90 条评论）

**摘要**：作者讲了一个极具体的场景：朋友开餐馆，用 Claude Code 给员工做了个任务管理 web app，此前没写过一行代码，界面干净、流程合理、数据能持久化，很自豪。作者上手一查——**没有响应式布局**（员工用的手机上直接崩）、没有登录（不知道谁干了什么）、没有设置、没有翻译（厨房里一半人不讲这个语言）、没有错误态、没有空态/重复态/两人同时编辑的冲突处理。数据的「持久化」只够扛一次刷新。**结论：那是一个漂亮的点击原型（click dummy），不是产品**。作者给出的核心比喻是安全带与气囊——**车里最该存在的部件，绝大多数时候什么都没做；软件的大部分代码就是安全带**。而朋友的理解是「它 100% 按预期工作，所以 90% 的活干完了，剩下只是托管」。对照的 ExitPath 帖里，同一种乐观更直白：一条高赞评论说自己让 AI 重写了 Microsoft / Asana / Zendesk / Adobe 生态的替代品，「不到一周、25 美元 token」，并补了一句「它大概短期内不会上线，但按这个速度……」

**开源之道点评**：这篇讲的表面是「AI 写不好软件」，实际讲的是**成本的可加性与否**。

原型的成本趋近于零，这是真的；但**原型的成本从来没有构成软件总成本的主要部分**，它一直是那笔用来换取决心的首付。AI 把这笔首付取消了，于是**唯一还在起作用的价格信号消失了**——在那之前，做错方向的代价会在写代码的几个周里逐步显现，让人中途停下；现在方向错了也是一天出活，错误被推到了「上线之后」。用科斯的语言：**企业存在的原因是它比市场更省交易成本**；AI 把「自己做」的成本压低后，本该更多的事被拉进「自己做」这一侧，但**拉进来的只是生产环节，验收环节还留在原处**，结果是一个失衡的组织形态。

但我必须指出这篇文章的一个盲区，因为它恰好是「开源之道」该补的那块：**作者把「维护」当成了一个技术清单**（响应式、登录、错误态、i18n、冲突处理）。这份清单可以背下来，可以被 AI 学会，甚至可以被自动生成。**真正不能被生成的那一项，他在文里一句没提——当系统开始影响真实的人（员工的排班、工资、考核），谁来对它的判断负责？** 这跟 11-18 那条 HN 帖子（《所有 AI 生成的代码都应当是开源的》）其实是同一问题的两个面：那份主张问「新产出的东西该归谁」，这篇问「新产出的东西该谁修」，**两者都绕过了第三问：它出错时谁承担**。用奥斯特罗姆的话说，公地的三项规则里，边界规则与分配规则都好写，**问责规则最难写，因为它必须先有一个「谁」**。

AI 在这里起了什么作用？它同时压低了两样东西的成本：**写代码的成本**和**发布代码的成本**。当后者逼近零，一个组织「开源」的行为就与「写博客」在制度形态上趋同——**产出、挂出、结束，不需要回应任何人的问题**。四十年前，「开源」这个动作之所以有制度重量，是因为它**隐含了一个承诺：有人在门后**。这个承诺从来没有被写进任何许可证，它一直靠成本结构撑着——**维护一个开源项目很贵，所以宣称开源的人，多半是认真的**。AI 拆掉的正是这根撑杆。

所以真正的制度问题是：**当「开源」的信号成本趋近零，接收方用什么来区分「有人在门后」和「只是挂出来」？** 现在能用的替代信号只有三个，而且都还很弱：**①被合并的外部 PR 里，出现了非原组织的账号**（11-16 看 IRS Direct File、11-18 看 AgentRun 用的都是这条）；**②issue 区里有维护者的第二次回复**，而不只是关闭；**③CODEOWNERS / MAINTAINERS 里出现了第二个组织**。三条都是**行为证据，不是文书证据**——这恰好是本周两份材料的共同结论：OpenAlex 那份 DAO 论文说「透明可追溯的决策记录」是优点，但那只是**结果的透明**；判断一个项目是不是公地，要看的是**在结果形成之前，有没有第二个人被允许说话**。

用赫希曼补一句收尾：这 68 个零 issue 的仓库不是「退出」也不是「发声」，它们是**从未进入**（never entered）。而一个从未有人进入的项目，讨论它的「治理健康」本身就是范畴错误——**它没有制度，它只有版本历史**。
