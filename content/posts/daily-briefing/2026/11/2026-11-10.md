## 「开源之道」 2026-11-10 搜集事件和材料

{{< figure src="/media/covers/daily-reading-2026-11-10.jpg" title="「开源之道」昨日阅读 · 2026-11-10" width="100%">}}

> 今天这份落在一条很具体的线上：**当产出速度超过核对速度时，组织不会停下，它会重新分配「谁签字」。**
>
> ① **先看一份把仓库里的文本当作制度载体来度量的实证。** `AGENTS.md`、`CLAUDE.md` 这类指令文件，每个 agent 会话都要读一遍。732 条轨迹测出来的结论很硬：过期指令会让 agent 照着错的做，**有时即使正确信息就在手边**；而 agent 一般能从失败里恢复，**但没有一个去修那份文件本身**。文档债的利息，不由维护者付，由每一个后来的会话按次付。
>
> ② **再看 agent 的自我改进到底改了什么。** 修 harness（提示、工具、记忆、控制循环）确实贡献增益——**harness 就是 agent 世界的制度**。但开放权重模型落后最多的地方，恰恰是输出必须通过物理稳定性或精确正确性严格检验的任务。不是能力上限问题，是**可验证性基础设施**问题。
>
> ③ 动态侧一条总量信号：LF Research 测出 **58% 的团队发版快过安全评审**，AI 助手让 60% 的团队外部包变多，而**这些包引入的传递依赖只有约一半会被审查**。同一时间，OpenSSF 加入 MOSAIC，其首要目标被写成「就 MOSAIC 的定义达成总体共识」——**一个协调组织的第一项产出是先谈拢定义，这句话本身就是现状诊断。**
>
> Project Pulse 今天的样本是 Unleash：12 年的 AGPL-3.0 加一份带 `relicense` 条款的 CLA。它给出的治理答案与前几天的三份都不同——**产权在入口处就用一张纸划清了，将来可能发生的争执在源头被解决掉。**

### 📄 论文两条

#### 1. 当 AGENTS.md 过期：文档债的利息不是维护者付，是**每一个后来的 agent 会话付**

**When Instruction Files Go Stale: Documentation Debt and Hidden Cost in Coding Agents** · Tural Mehtiyev、Biruk Tadesse、Lawrence Arkoh、Wesley Assunção（arXiv:2611.09802，cs.SE/cs.AI，2026-11-06）

**链接**：[arXiv:2611.09802](https://arxiv.org/abs/2611.09802)｜DOI [10.48550/arXiv.2611.09802](https://doi.org/10.48550/arXiv.2611.09802)

**摘要**：Claude Code 这类编码 agent 由仓库里的指令文件（也叫上下文文件、agent 配置文件）引导——`AGENTS.md`、`CLAUDE.md`——这些文件**每个 agent 会话都要读一遍**。和任何文档产物一样，它们会落后于代码：测试目录搬家了，文件还指着旧路径。按技术债的术语，过期的指令是**文档债**，而它的**利息就是它给之后每一次 agent 会话增加的额外成本**。作者从三个活跃开源仓库里取了三类真实过期指令（一个测试命令、一个代码位置、一个新增组件的步骤），各做三个版本（保持过期、改成当前路径、直接删掉），代码与任务保持不变，让 agent 执行 22 个维护任务，分析两个模型共 **732 条轨迹**的逐次工具调用。结论三条：**其一**，只要过期指令与任务相关，agent 就会照着它做，**有时即使正确信息就在手边**；**其二**，在过期测试命令那一组，Claude Sonnet 5.5 每次运行多花约**两次额外工具调用**，比用改正版多出**三分之一**，另两组未测出差异；**其三**——这条最重要——**agent 一般都能从眼前的失败里恢复过来，但没有一个去修那份指令文件本身**。改正版消除了对废弃路径的操作，删掉版阻止了绝大多数。作者的落点是：**只看任务成功率，会掩盖文档债的成本**。

**「开源之道」点评**：这是今年第一篇把"仓库里的文本"当作**制度载体**来度量的实证论文，而不是把它当作提示工程技巧。`AGENTS.md` 在今天的仓库里已经不只是文档——它是**契约**：它告诉每一个进入项目的 agent"这里的规矩是什么、测试怎么跑、组件怎么加"。而这篇论文测出来的是：**契约一旦失修，成本不出在签约双方的任何一方身上，而是摊销到了每一个后来者的会话里**。这正是奥斯特罗姆讲公地治理时最容易被忽略的那一条——**规则的维护本身是一项要有人出的成本**；当没有任何人被指派维护规则、也没有任何机制把"修规则"记成贡献时，规则就会一直烂下去，而每一次使用都在为这份烂付费。

把结论翻译成制度语言，只有一句话：**agent 不会维护制度，它只会遵守制度**。研究者给了 22 个任务、三次机会、两类模型，**没有一次**出现过"顺手把过期的 AGENTS.md 改掉"这种行为。这不是模型不够聪明，是激励结构里**根本没有这一项**——任务的验收标准是"维护任务完成"，不是"规则被修正"。威廉姆森讲治理时把"适应（adaptation）"当作制度的核心功能，而适应的前提是**有人拥有修改规则的权力并且承担修改的责任**。在 AI 参与的仓库里，这个角色目前是空的。于是出现一个精确的新债种：**指令文件的债不由作者承担，由所有未来的读者按次支付**——它比传统的文档债更贵，因为传统文档债的读者是人，人是会自己查代码的；而这里的读者是 agent，**它会忠实地照着一份错的规矩做，并且做得很快**。

这与昨日 curl 的处置是同一个方向的两种流速：**当维护能力跟不上时，成本不会消失，只会被重新分配给那些没有谈判能力的一方。** 区别只在流速——curl 那边维护者主动把 LOW/MEDIUM 报告转公开以分摊认定成本，是显性的、被记录在案的退让；这里的退让分散在几千次会话里，没有人记账。

#### 2. Agent 的自我改进：能改的是 harness，改不动的是「严格检验」那一关——开放权重模型落得最远

**Flex-RSI: Benchmarking Recursive Self-Improvement of Frontier Agents** · Jingdong Zhang、Jionghao Wang、Zhengming Yu、Yancheng Cai、Wei Chow、Chris Choy、Zhiyang Dou、Hang Hua、Jiachen Li、Zhixuan Liu、Chen Wang、Songlin Wei、Siyuan Yang、Yu Yuan、Xiaohang Zhan、Yucheng Zhang、Shuhong Zheng、Xin Li、Lingjie Liu、Wojciech Matusik、Zhengzhong Tu、Wenping Wang（arXiv:2611.08946，cs.AI/cs.CV/cs.RO，2026-11-06）

**链接**：[arXiv:2611.08946](https://arxiv.org/abs/2611.08946)｜DOI [10.48550/arXiv.2611.08946](https://doi.org/10.48550/arXiv.2611.08946)

**摘要**：前沿语言模型正在被当作 agent 部署，而 agent 的表现不只看模型，还看它的 **harness**：提示、工具、记忆、控制循环。当 agent 被用到一个新问题上，一个自然的问题是——**它能不能用任务的反馈来改进自己的做事方式，而不只是改进这一次的答案**。现有基准大多固定 harness 只评产出，或者只针对大规模模型训练。作者提出 **Flex-RSI**：在固定预算下评测 agent 在视觉与机器人任务上的**递归自我改进**。每一轮，一个 executor 改进任务解法，只有当它在留出验证集上得分更高时才被保留；随后一个 improver 修订 harness，**包括 executor 和它自己**。每个 run 都从同一个通用 harness 出发，最终解法在隐藏测试集上评分。结论三条：**其一**，当 agent 自己构建解法时，自我改进的效果最大；**其二**，**只记录成功/失败二值反馈的做法会拖住开放权重模型**；**其三**，**开放权重模型落后最多的地方，恰恰是输出必须通过物理稳定性或精确正确性严格检验的任务**。配对实验进一步显示，**修改 harness 本身**确实贡献了增益。

**「开源之道」点评**：这篇论文最值得开源圈注意的一句是"修改 harness 本身贡献了增益"——**harness 是 agent 世界的制度**：它规定了什么算完成、什么算合格、反馈怎么给。开放权重阵营在"改进 harness"这一层跟得不慢，但在"严格检验"这一层掉得最远。这不是一个新发现，但它用基准的形式把一个直觉定量了：**开源模型缺的从来不是能力上限，是可验证性基础设施**。物理稳定性、精确正确性这类判据，要求的是昂贵的仿真与人工标注——**这些恰恰是公地最难自发供给的东西**。

把三条结论连起来读，指向一个相当冷的判断。自我改进的收益主要来自**改制度（harness）**，而不来自**改答案**；但**制度能不能被验证有效**，取决于有没有一套严格的、外部的判据。于是形成一个闭环：**能自己定义"什么算好"的 agent 进步最快，而定义"什么算好"的权力本身不是免费的**。开放权重模型的处境因此不是"算力不够"，而是——**它被放进了一个判据由别人设定、且判据的构建成本落在别人手里的评测场**。

这与大分流 2.0 的判断是同一个机制，只是换了个场地：**你可以在自己的场地上自由地改进，但出不了你无法独立验证的那道门**。这里的问题不是"谁更强"，而是**谁有权认定什么算通过**——而这一条，从来不在权重里，在评测集里。

### 📰 开源动态

#### 1. LF Research 新报告：58% 的团队发版快过安全评审，60% 说 AI 助手增加了外部包——但**间接依赖只有一半的时候会被看**

**来源**：[LF Research《State of AI Impact on Software Security and Cybersecurity 2026》官方页 2026-11-09](https://www.linuxfoundation.org/research/ai-impact-on-cybersecurity-2026)（作者 Sam Boysel，序言 Laura Guazzelli/OpenSSF，DOI **10.70828/TEZV6255**，开放数据 Zenodo records/23810645）｜[PR Newswire 2026-11-09 新闻稿](https://www.prnewswire.com/news-releases/ai-is-writing-code-faster-than-security-can-review-it-finds-new-linux-foundation-research-sponsored-by-activestate-302931650.html)

**摘要**：这份报告由 LF Research 与 OpenSSF、ActiveState、LF AI & Data 合作完成，配套 DOI 与 Zenodo 开放数据（可作为纵向比较的面板）。核心数字：**AI 编码工具把安全开发速度提升 17%，但扫描工具产生的假阳性把工作量推高 30%**；**3/5 的团队发版速度已经超过安全评审能跟上的速度**（新闻稿口径为 58%）；**82% 的从业者警告过度依赖 AI 工具正在削弱开发者的安全技能**；**60% 表示 AI 编程助手增加了代码库中的外部包数量，而这些包引入的传递依赖（transitive dependencies）只有约一半的情况会被审查**。正面结论只有一条：**设立了专职 AI 安全角色与正式政策的团队，在新兴威胁上的准备度显著更高**。

**「开源之道」点评**：这份报告里最有制度含量的是最后那句"只有一半的时候会被看"——**它不是能力问题，是边界问题**。直接依赖你写了 `package.json`，间接依赖是别人写的 `package.json`。开源供应链之所以是一个治理难题，从来不是因为看不见，而是因为**责任被引用的次数稀释了**：你引用 A，A 引用 B，B 引用 C，出问题时没有任何一个人或组织在自己的账本上记着 C。

报告测出的 58% 与 30% 假阳性是一回事的两面——**当工具产出报告的速度超过人核对的速度时，组织不会停止发版，它会降低核对标准**。这就是 curl 那条政策变更在全体组织层面的镜像：**个体的退让是显性的、被记录在案；组织的退让是隐性的、被记成"效率提升"**。而"设立专职 AI 安全角色后准备度显著更高"这一条，用威廉姆森的话说就是：**当交易频率与不确定性同时上升时，唯一有效的应对是新建一个治理岗位，而不是再加一条流水线。**

#### 2. OpenSSF Q4 三件事：加入 MOSAIC、发一份"用 AI 找洞和修洞"的开发者指南、把 Zarf 推到 1.0——**外加一个值得警惕的措辞**

**来源**：[PR Newswire / OpenSSF 官方新闻 2026-11-09](https://finance.yahoo.com/technology/ai/articles/openssf-welcomes-members-expands-ai-160000722.html)｜[OpenSSF《Finding and Fixing Software Vulnerabilities Using AI》2026-10-20](https://openssf.org/blog/2026/10/20/new-openssf-guide-finding-and-fixing-vulnerabilities-using-ai/)｜[Zarf 1.0 公告 2026-11-09](https://openssf.org/blog/2026/11/09/announcing-zarf-1-0-security-and-stability-for-airgap-software-delivery/)

**摘要**：OpenSSF 宣布新会员 **Beautiful Majestic Dolphin、DevGuard、UElement Technologies**（General Member 级别），并公布 Q4 的几项动作：**①** 加入 **MOSAIC（Multi-Organization Secure AI Coordination）**，目标是与其他倡议做标准化映射、对齐 NIST SP 800-53 的 SC-42 控制项、在 MOSAIC 的定义上达成共识；**②** 发布《用 AI 发现并修复软件漏洞：开发者指南》，由 Best Practices 与 AI/ML 工作组共同产出，明确写"**AI 生成的补丁在未经自动化测试与人工复核之前绝不应被信任**"，并计划配套课程 LFD126；**③** 与 LF Education 推出 **Secure AI Associate (SAIA)** 认证；**④** GitHub 把 OpenSSF 的 Malicious Packages 数据接入 Advisory Database，Dependabot 的恶意包告警扩展到 8 个生态；**⑤** **Zarf 1.0** 发布，强化包签名与验证、配置管理，并"为长期兼容性与社区驱动开发建立基础"。官方引用 Laura Guazzelli 的话："**这条新的 SDLC 已经把『发现漏洞』与『自动化攻击』之间的窗口压塌了**"，并点名 **EU CRA** 让报告窗口进一步收紧。

**「开源之道」点评**：这条的价值不在新会员（三家 General Member 对治理结构没有实质影响），而在 **MOSAIC 那一段的措辞**——"a general consensus on MOSAIC definitions"。**一个协调组织的首要产出，是先把定义谈拢**，这句话本身说明了现状：AI 安全领域现在有 N 套框架、N 套术语，互相之间连"什么叫风险"都没有共识。而在所有框架对齐工作里，最贵的一步从来不是写规范，是**让不同出资方接受同一套判据**。

第 ⑤ 条容易被滑过去却很重要：**Zarf 1.0 是 OpenSSF 里少数有明确"1.0 + 长期兼容性承诺"的项目**——对断网/气隙环境交付软件听起来很小众，但它服务的是国防、能源、医疗这些**无法用 SaaS 兜底的场景**，也就是开源公地被要求"必须自己站得住"的那些地方。

至于那份指南的核心句"AI 补丁未经测试与人工复核不得信任"——**这句话和 curl 的做法构成了一个完整的制度分工**：基金会层面把判据写进文本，项目层面把无法承载的判定权让渡出去。两者都不解决问题，但两者都在做同一件事：**在新的产出速度下，重新分配"谁签字"这件事。**

### 🔍 Project Pulse

#### Unleash（Unleash/unleash）— 12 年的 AGPL 项目把 CLA 一路签下来，这不是意外，是**商业模式的宪法**

**实测数据（2026-11-10 抓取 GitHub API）**：stars **14,284** ｜ forks **933** ｜ watchers **74** ｜ open issues+PRs **39** ｜ license **AGPL-3.0** ｜ created **2014-09-29** ｜ pushed **2026-11-09T18:08Z** ｜ releases：v8.1.0(08-05) → v8.2.0(09-08) → v8.2.1(10-22) → v8.3.0(10-27) → v8.3.1(10-29)，**全部由 `github-actions[bot]` 发布** ｜ 仓库根目录有 **`CLA.md`**，无 `GOVERNANCE.md`、无 `MAINTAINERS.md`

**【L1 · 版本与活动】** 发布节奏近期明显加密：8 月与 9 月各一个 minor，10 月出了 8.2.1 + 8.3.0 + 8.3.1 三个版本，**10 月 22 日到 29 日七天内三个版本**。语义化版本与自动 tag 化已经完成（release 由 bot 触发，代表 tag 流程已进 CI）。近期提交密度：最近 100 个 commit 覆盖 **11-04 12:37 至 11-09**（约五天），作者 19 人，其中 `krzychukula` 13 次、`ppicom` 13 次、`zagorski` 12 次、`thomasheartman` 9 次、`dharmadeveloper108` 8 次、`adrian2x` 8 次、`dependabot[bot]` 7 次。**贡献面很宽，但全部集中在同一个核心圈。**

**【L2 · 治理结构——今天的核心信号】** 三件可验证的事：

1. **仓库里没有 GOVERNANCE.md，但有 CLA.md。** 这份 CLA 的第 2 条原文授予 Unleash "a perpetual, worldwide, non-exclusive, no-charge, royalty-free, irrevocable copyright license to reproduce, prepare derivative works of, publicly display, publicly perform, sublicense, **relicense**, and distribute your Contributions"。**`relicense` 这个词是整份文件的枢纽**——它意味着项目方可以把社区贡献重新授权到 AGPL 之外（例如商业授权），而贡献者本人拿不到对价。这不是暗箱操作：`contributing/CONTRIBUTING.md` 明写"**在合并任何 PR 之前，每一个人类贡献者都必须阅读并同意 CLA**"，并且 CLA 检查会对每个 PR 触发。**制度是公开的、可读的、写清楚的。** 但它与 gVisor（11-07 简报）、NVKE（11-09 简报）都不同——那两家至少在争议的是**谁有权裁决**，Unleash 这里裁决权的问题根本不需要讨论，因为**产权在入口处就已经用一张 CLA 划清了**。
